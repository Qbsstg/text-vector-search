# 文本向量化与检索：前期调研与项目启动分析

日期：2026-10-22。依据：题目 PDF v3.3 的全部 3 页、本机开发环境检查、文末列出的官方资料。

本文是设计建议和后续实施依据，尚未创建应用骨架、执行数据库 DDL、开展运行验证或性能测试。题目中的编码、提交、部署等要求作为未来交付要求整理，本次工作范围是调研和启动分析。

## 1. 项目判断

这是一个以 AI 应用为背景的 Java 后端工程实践题。主要难点是异步任务、并发一致性、数据持久化、边界校验和可验证性。模拟向量算法需要体现文本相似性，但不要求实现语义理解。

建议实现一个单进程 Spring Boot 服务：H2 保存文档、向量、任务和统计数据；Java 有界队列调度后台计算；同步检索使用精确扫描和 Top-K 小顶堆。先完成可解释、可恢复、可测试的闭环，再根据实测考虑缓存等优化。

## 5. 模拟向量化算法

### 5.1 推荐流程

1. 保留原始文本用于详情和溯源；向量化前执行固定规范化策略，例如 NFKC、`Locale.ROOT` 小写、空白归一化。
2. 按 Unicode code point 提取 unigram 和 bigram。单字符也能产生特征，中文不依赖额外分词器，emoji 不被拆成半个代理对。
3. 给特征加上长度前缀，使用固定哈希规则映射到 256 个桶。可用 SHA-256 的不同字节分别生成桶编号和正负符号；不要跨线程共享可变 `MessageDigest`。
4. 每个桶先用整数累计特征频次，再按固定下标顺序进行浮点计算，避免并行浮点归约带来的不确定性。
5. 做 L2 归一化，输出新的 `float[256]`。若范数为 0，直接返回全零向量。
6. 记录 `embeddingVersion`，把规范化、特征、哈希、权重、归一化规则固化为一个版本。

这是一种借鉴特征哈希的模拟方案，算法依据见原论文 [S5]；具体 n-gram 组合和 256 维效果需要在本题样例中验证。不能把字符相似性描述为真正的语义理解，也不能承诺无关文本一定低分。256 维存在哈希碰撞，符号累计还可能抵消。

示例验收语料可选“Java 后端开发”“Java 后端开发工程师”“周末去海边散步”，同时覆盖同文、局部改写、无关内容、中英文、emoji 和空白。对相似度次序的断言基于固定样例，不能声称对任意文本都成立。

### 5.2 候选算法比较

| 方案 | 适配情况 |
| --- | --- |
| 整段文本哈希后生成伪随机向量 | 确定性容易，但微小文本改动会丢失相似性，不适合作为首选 |
| 词典型 TF-IDF | 有可解释性，但词表/IDF 随语料变化会影响既有向量，需额外版本管理 |
| SimHash | 更适合二进制指纹和汉明距离；本题明确要求 256 维 float 数组 |
| n-gram 特征哈希 | 不需要训练和动态词表，固定维度，适合本题的文本相似性模拟 |

### 5.3 CPU 耗时模拟

不能只用 `Thread.sleep` 冒充 CPU 计算。建议通过固定轮数的摘要/特征计算产生可配置计算量，计算结果参与后续计算，避免无效循环。以固定输入和轮数复现结果，轮数影响向量时必须纳入算法版本。

入库与查询复用同一个向量化入口和参数。题目明确查询接口同步，因此查询也会承担计算成本，不能为了“查询快”悄悄换成另一套算法。工作线程数与计算轮数需要联合测量，防止后台任务耗尽 CPU。

算法耗时、吞吐量和合理线程数目前均未实测，不能写成性能结论。

## 6. 数据模型和接口草案

### 6.1 两张核心表

`documents`：

- `document_id`：用户传入的字符串主键。
- `raw_text`、`channel`：原文和渠道，渠道缺省为 `default`。
- `submitted_at`、`vector_completed_at`：提交和向量化完成时间。
- `invalidated`、`invalidated_at`：独立的失效状态。
- `vector_bytes`、`embedding_version`：向量内容和算法版本。
- `hit_count`：`BIGINT`，初值 0。

`embedding_tasks`：

- `task_id`：服务生成的 UUID，作为字符串暴露。
- `document_id`：外键；第一版按“一篇文档一个任务”加唯一约束。
- `status`：`QUEUED / RUNNING / SUCCEEDED / FAILED`。
- `submitted_at`、`started_at`、`finished_at`。
- `error_code`、`error_message`；恢复次数可作为诊断字段。

第一版拒绝重复文档 ID，因此任务不必复制一份可变文档内容。未来如果允许覆盖或重试，需要重新设计版本关系，防止旧任务覆盖新文本的结果。

`vectorReady` 从向量存在和成功状态推导，不另设一个可独立写入的布尔字段。完成事务同时写入向量、完成时间和任务成功状态，保证这些信息一致。

向量建议使用固定字节序编码为 1024 字节，即 `256 × 4`。H2 可采用 `VARBINARY(1024)` 并增加实际长度检查，MyBatis 用独立 codec/type handler 转换，往返测试要求逐位一致；不使用 Java 对象序列化。H2 类型支持见 [S6]。

索引初步考虑任务的 `(status, submitted_at, task_id)`、任务关联文档的唯一键、文档的失效/渠道组合索引。最终索引按实际查询和 `EXPLAIN` 决定。

### 6.2 API 草案

| 方法/路径 | 用途 | 主要行为 |
| --- | --- | --- |
| `POST /api/documents` | 提交文档 | 输入 `documentId/text/channel`，事务提交后返回 `202 + taskId` |
| `GET /api/tasks/{taskId}` | 查询任务 | 返回状态、时间、失败原因；成功后关联文档信息 |
| `GET /api/documents` | 分页列表 | 可按渠道、失效状态等过滤，默认不返回整个向量 |
| `GET /api/documents/{documentId}` | 查询详情 | 原文、元信息、向量是否就绪、任务状态、命中次数 |
| `PUT /api/documents/{documentId}/invalidation` | 标记失效 | 幂等，不存在返回 404；重复失效不改变首次失效时间 |
| `POST /api/search` | 同步检索 | 输入 `text/topK/channel`，返回按相似度降序排列的结果和来源元信息 |

不单独增加统计面板或分析接口：题目要求的溯源统计先通过详情、列表和检索结果中的元信息满足。

## 7. 异步任务：可靠接收与后台计算

建议把 H2 任务表作为任务的持久化依据，Java 队列作为进程内执行缓冲。任务状态中的“排队中”同时包括已入库、尚未放进内存队列的任务。

```text
提交请求 -> 校验/容量检查 -> 同事务保存文档和 QUEUED 任务 -> 返回 202
                                |
                         单个调度器定期扫描
                                v
                 有界线程池队列 -> Worker -> 成功/失败事务
```

### 7.1 调度和事务边界

1. 提交事务只保存文档和任务，不做向量化。成功返回意味着任务已持久化。
2. 调度器扫描已提交的 `QUEUED` 任务，按提交时间和任务 ID 稳定排序，小批量放入线程池。
3. 用线程安全的在途 ID 集合去重，避免每次扫描都把同一个任务重复塞进队列；入队失败时清理集合。
4. Worker 用条件更新领取任务：只有 `QUEUED -> RUNNING` 更新成功者才能计算。数据库状态才是最终防重依据。
5. 计算在事务外进行，不长期占用数据库连接或行锁。
6. 计算成功后短事务更新向量、完成时间和任务 `SUCCEEDED`；失败则记录 `FAILED` 和可读原因。
7. Worker 结束清理在途集合。单次异常不能导致调度器永久停止；数据库无法记录最终状态时需暴露健康异常，不能伪报成功。

这解决了“先写数据库再入队，中间崩溃会丢调度”和“先入队再提交，Worker 读不到记录”两类问题。周期扫描负责兜底，提交后的主动唤醒只作为延迟优化。

### 7.2 队列满与提交限流分开处理

- 内存队列满：调度器暂缓派发，任务继续保持数据库中的 `QUEUED`，后续继续调度。
- 持久化未完成任务总量达到配置上限：新请求返回 `429`，不创建文档和任务。
- 在单进程前提下，可用提交互斥锁包住“计数、检查、写入、事务提交”，避免并发超额接收。锁必须覆盖真实提交边界，不能在 Spring 事务代理提交前就释放；可用 `TransactionTemplate` 明确边界。
- 线程池使用 `AbortPolicy`，由调度器处理拒绝。丢弃策略会隐藏任务；若直接从 HTTP 请求使用 `CallerRunsPolicy`，饱和时会让请求线程执行耗时计算，破坏异步接收预期。[S3]

队列容量、未完成任务总量、线程数和文本大小都需要限制。这里只提出可配置边界，具体默认值在启动原型测量后确定。

### 7.3 重启恢复与关闭

状态主路径为 `QUEUED -> RUNNING -> SUCCEEDED / FAILED`。

启动时先初始化数据库，再把上次进程遗留的 `RUNNING` 恢复为 `QUEUED`，最后启动调度器和接收请求；原有 `QUEUED` 自然继续扫描。该恢复仅适用于本方案的单实例前提。

计算可能因崩溃重做，因此采用“至少执行一次计算 + 幂等结果提交”的描述，不承诺计算恰好一次。普通业务失败进入 `FAILED`，第一版不做无限自动重试，也不额外实现手动重试接口。

关闭时先停止接收和调度，再等待在途任务有界完成，最后关闭数据源。尤其应避免任务尚在写 H2 时粗暴中断 JDBC 线程，H2 文档明确提示嵌入式模式下线程中断的文件访问风险。[S7] 需要进程崩溃验收时，使用独立子进程和独立测试数据库。

## 8. 检索、失效和计数的一致性

### 8.1 检索与 Top-K

1. 同步计算查询向量。
2. 从 H2 读取任务已成功、向量已就绪、未失效、算法版本匹配的文档；传入渠道时先做渠道过滤。
3. 取出本次候选快照，在请求私有的数据结构内计算余弦相似度。
4. 使用容量为 K 的小顶堆维护结果，最后再按完整排序规则输出。
5. 只对最终返回的文档更新命中次数，统计事务失败则整个检索返回业务失败。

维度固定为 D=256 时，计算/选择复杂度为 `O(ND + N log K + K log K)`。堆空间为 `O(K)`；若第一版一次加载全部候选向量，总内存仍为 `O(ND)`，不能把整次检索空间误写成 `O(K)`。

每条向量的原始载荷为 1 KiB，1 万条约 9.8 MiB，尚不包括数据库、Java 对象和请求复制开销。这是容量估算，不是性能测试。数据规模和并发量题面未给出，先测试目标样本量，再决定是否改为流式读取或增加内存索引。

首版使用 H2 作为唯一业务数据来源，避免一开始引入持久层与共享向量缓存的双写一致性问题。内存中的队列、去重集合和每请求向量仍需保证并发安全；若后续增加索引，需要不可变快照、重启重建和提交后更新机制。

### 8.2 排序和零向量

- 完整排序规则：相似度降序，相同分数按文档 ID 升序。堆顶必须表示这一规则中的最差候选，平分时也要比较 ID。
- 一侧向量范数为 0 时，相似度定义为 0，不能产生 `NaN` 或无穷大。
- 第一版不加相似度阈值，0 分和负分仍可进入 Top-K，结果数量为候选数量与 K 的较小值。
- 据此，空查询产生零向量，仍返回稳定排序的 0 分 Top-K。这是建议业务约定，题面只规定空文本向量为零，未单独规定空查询的返回形式。
- 运算累加使用 `double`，对浮点误差导致的轻微越界可钳制到 `[-1, 1]`；输入向量和结果须检查有限数值。

### 8.3 三个必须讲清楚的并发场景

**任务完成与失效并发**：失效只更新失效字段；向量完成只更新向量和完成信息，不能整体覆盖旧文档快照。文档在排队或计算时被失效，任务可继续完成，最终状态可以同时是“任务成功、文档失效”，仍不能参与新的检索。

**检索与失效并发**：建议第一版定义候选快照语义。失效操作完成后新发起的检索必定排除该文档；与失效重叠的检索可能返回其先前读取的有效文档。这是明确的语义选择，不能声称实现了“并发失效后所有在途结果立即消失”。若要求后者，需要另行设计串行化/锁或结果二次确认，并评估吞吐成本。

**多个检索同时命中**：使用数据库原子语句 `hit_count = hit_count + 1`，避免先查后写的丢失更新。只累计最终 Top-K，每次检索每篇至多一次。涉及多行时按固定文档 ID 顺序更新，降低交叉加锁导致的死锁风险。

命中定义为应用成功完成结果选择和计数提交，不承诺客户端实际收到了网络响应；客户端重试会作为新的检索再次计数。与失效重叠的快照命中也可累计，计数更新不改变失效字段。

## 9. 题面未明确的规则：建议先固定

| 问题 | 第一版建议约定 |
| --- | --- |
| 文档 ID 重复 | `409 Conflict`，不覆盖、不另建任务；数据库唯一约束兜底 |
| 原文 `null` / 空字符串 | `null` 返回 400；空字符串合法，产生零向量；不要给文本直接加 `@NotBlank` |
| 纯空白文本 | 按固定规范化规则处理为空向量，原始文本保留 |
| 文档 ID 空白 | 400，明确长度上限；文档 ID 统一按字符串处理 |
| 渠道未传/空白 | 归一化为 `default`；有效渠道按大小写敏感精确过滤 |
| topK 为 0、负数、非整数或超上限 | 400；合法 K 大于候选数时返回全部候选 |
| 文档/任务不存在 | 404 |
| 重复标记失效 | 幂等成功，保留首次失效时间 |
| 失效文档能否恢复 | 第一版不提供恢复接口 |
| 失败任务能否重试 | 第一版查询失败原因即可，重试属于扩展 |
| 计数提交失败 | 不返回检索成功，使用统一错误结构 |
| 时间格式 | 内部用 `Instant`，接口用 ISO-8601 UTC；显示层可转换时区 |
| 文本、分页、队列、积压上限 | 全部配置化；初始值通过原型测试确定 |

这些是设计建议，不应写成 PDF 已明确规定。实现前应把最终约定固化到接口说明和测试。

## 10. 数据库与项目组织

数据库 URL 建议为 `jdbc:h2:file:${APP_DATA_DIR:./data}/vector-search`，记录相对路径按工作目录解析这一点；交付时建议传入稳定的绝对数据目录，避免从不同目录启动后误以为数据丢失。[S7]

首版使用 `schema.sql` 和 `spring.sql.init.mode=always` 自动建表，脚本采用幂等 `CREATE TABLE/INDEX IF NOT EXISTS`，DDL 失败应阻止启动。自动建表不等于支持任意历史结构升级；出现真实表结构演进时再引入单一迁移机制。若改用 JPA，避免与 Hibernate 的 `create/create-drop` 混用，否则会破坏数据保留预期。[S8]

项目结构建议如下，当前尚未创建这些应用文件：

```text
pom.xml / mvnw / .mvn/
src/main/java/.../
  api/             请求响应 DTO、Controller、统一异常处理
  document/        提交、查询、失效服务
  task/            调度器、Worker、恢复、状态流转
  embedding/       确定性算法、向量 codec
  search/          相似度、Top-K、计数
  persistence/     MyBatis Mapper、数据对象
  config/          队列和参数配置
src/main/resources/application.yml / schema.sql
src/test/java/.../
docs/              设计、接口、验收、AI 关键对话
scripts/           启动和验收脚本
README.md
```

提交时忽略 `target/`、`logs/`、运行数据库、临时渲染文件和本机配置；提供源码、DDL、启动说明和真实 Git 记录。压缩包需要保留可检查的提交历史，或另外给出仓库地址，不能只交没有历史的源码导出。

## 11. 实施顺序与验收门槛

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| M0：环境与数据库原型 | 锁版本、最小启动、H2 DDL、向量 codec | JDK 17 构建；连续启动不清数据；float 编解码逐位一致 |
| M1：确定性算法 | 向量器、余弦、Top-K | 256 维；同文稳定；空文本全零；并发调用无串扰；Top-K 与参考排序一致 |
| M2：异步入库 | 提交、持久化状态、队列、Worker、任务查询 | 计算未放行时提交也能返回；待完成文档不可检索；失败可查 |
| M3：检索和管理闭环 | 同步检索、渠道过滤、列表/详情、失效、计数 | 过滤在 Top-K 前完成；只统计最终结果；失效不被完成任务覆盖 |
| M4：并发与恢复 | 压力边界、积压上限、崩溃恢复、关闭流程 | 并发计数不丢；重复派发只成功领取一次；重启后继续处理未完成任务 |
| M5：交付整理 | README、接口示例、AI 对话、Git 时间线、干净打包 | 新目录按说明可启动并完成验收流程；部署加分项可在此阶段另做 |

建议每个阶段完成并验证后做真实 Git 提交，例如 `chore: bootstrap service and schema`、`feat: add deterministic vectorizer`、`feat: persist and execute embedding tasks`。不补造历史，不把全部代码最后一次性提交；本次调研没有初始化 Git 或创建提交。

## 12. 关键测试与待验证问题

重点测试：

1. 向量确定性：重复、多线程调用、不同进程/重启、codec 往返；规范化不依赖机器 Locale。
2. 纯算法：空向量、单字符、中英文、emoji、相同分数、负分、K 大于候选数；用全量排序作为小顶堆的参考结果。
3. 异步边界：用 latch/可控向量器阻止计算完成，证明提交已返回且文档不可检索；避免靠固定睡眠猜测状态。
4. 任务完整性：失败原因落库；已接收但尚未入队的任务可被扫描；重复派发只允许一次领取；拒绝新提交不产生残留文档。
5. 并发失效：人为阻塞计算，中途失效，放行后验证文档仍失效；分别验证失效完成后的新检索和在途检索语义。
6. 并发计数：多线程重复检索同一文档，实际计数与成功事务数一致；未返回候选不加计数；多行交叉命中不丢更新。
7. 文件持久化：独立临时文件目录下关闭并重启，验证文档、向量、任务、失效标记、计数均保留；运行中任务可恢复。
8. 资源边界：积压达到上限、超长文本、过大 K、通道无匹配、数据库写失败；验证响应和任务状态不会假成功或永久悬挂。

必须用原型消除的不确定性：

- 锁定的 Boot/MyBatis/H2 版本能否在 Java 17 上完整构建、自动建表并启动。
- H2 对向量二进制字段、条件更新和并发计数的实际行为。
- 目标样本量下候选读取的耗时、内存、CPU 竞争；队列容量、线程数和 CPU 模拟轮数的合理初值。
- 人为崩溃后任务恢复与状态回写是否满足约定；不能仅凭正常关闭后的重启测试声称已覆盖崩溃恢复。

## 13. 可用于面试解释的问题

- 为什么选择特征哈希，它模拟了什么，又缺少什么？256 维碰撞有什么代价？
- 为什么不能靠 `@Async` 注解或 `ConcurrentHashMap` 的名字就声称并发安全？
- 接收任务、提交事务和进入内存队列之间，进程崩溃会发生什么？
- 为什么区分内存队列容量与持久化积压上限？拒绝策略会改变什么行为？
- 如何保证向量、完成时间、任务成功状态同时可见？
- 为什么计算完成不能把已失效文档重新变成有效？
- 命中计数为何使用数据库自增，而非读改写或只有内存里的原子计数？
- 小顶堆相比全量排序节省什么？加载全部候选后，总内存复杂度是多少？
- 为什么采用单实例？增加实例后哪些锁、恢复逻辑和本地去重假设会失效？
- 如何用可重复的测试证明异步、并发和重启恢复，而非靠手工演示？
