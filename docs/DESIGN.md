## 1. 从题目约束确定边界

本题要求Java17以上、Spring、H2文件持久化、自带DDL并自动建表、Java实现队列，以及固定256维float的模拟向量化。提交文档异步处理，检索同步完成；同文必须确定，空文为零向量。项目将构建基线锁定为Java17，使用MyBatis显式表达事务内SQL。

重点是让“已接收、处理中、成功、失败、失效”有可靠的持久状态，并在并发和重启下维持一致性。字符向量只用于模拟字面相似；本项目不调用模型、不解析文件、不生成答案，也不实现完整RAG、多租户或分布式任务平台。渠道是来源标签，不是权限边界。

## 2. 技术选型及替代方案

| 问题 | 选择 | 理由与代价 |
| --- | --- | --- |
| 如何操作H2 | MyBatis + 显式条件SQL | JPA也符合题意；这里优先让领取条件、字段级更新、原子计数和受影响行数便于审查，不把JPA描述为不能保证一致性。 |
| 如何保存任务 | H2任务表 + 有界Java执行器 | 只靠内存队列会遗漏提交后、入队前崩溃的任务。数据库保存事实，扫描补派；代价是周期扫描和单文件数据库的吞吐边界。 |
| 如何限制执行 | 固定Worker、ArrayBlockingQueue和拒绝策略 | 相比每任务新建线程或无界队列，CPU和排队占用可控。拒绝入队不等于业务失败，已持久化任务仍保留。题目不允许引入MQ。 |
| 如何检索 | 全部合格候选精确评分 + Top-K堆 | 文档上限明确，精确结果更易验证。ANN、外部向量库会增加一致性和运维范围，当前不引入；代价是搜索随候选数线性扫描。 |
| 如何部署 | 单JVM、单H2文件、JAR同源托管前端 | 不需要Node运行服务、外部数据库或消息中间件。牺牲水平扩展，换取可追溯的恢复和文件锁边界。 |

### 为什么选字符N-gram与特征哈希

特征提取、加权、向量映射和相似度是不同层次，不将所有名称当作互斥算法。

| 候选 | 工程判断 |
| --- | --- |
| 整段SHA派生向量 | 确定且简单，但改一个字可能让整段表示完全变化，不能保留局部字面重合，作为反例而非主方案。 |
| 固定词表BoW / TF | 可解释，但词表外输入信息损失明显，中文通用输入需要额外维护规则。 |
| TF-IDF | 冻结词表、IDF及映射后可以满足确定性；动态更新语料统计会改变旧表示，当前没有冻结训练资产或重算机制。 |
| SimHash | 固定256位映射为±1 float是可行的，不能因它通常输出bit就否定题意适配。其近重复/汉明解释与本项目的稠密余弦接口不同，首版未采用。 |
| MinHash | 适合集合Jaccard；整数签名的float编码、精度及比较方式需要额外设计，不优先。 |
| 字符1/2-gram + 带符号特征哈希 | 无训练词表，中文、英文、emoji可用；共享片段产生可解释的相似性，单字符也有特征。256桶会碰撞、抵消，没有同义词或上下文理解保证。 |

最终选择最后一种。预研中的小样本Python实验只用于探索，不能当Java验收、语义准确率或普遍排名；实际实现以[冻结B1算法契约](design/b1-algorithm-contract.md)为准。更早的[候选方案研究](前期调研/01-文本向量化算法方案对比与选型报告.md)保留其当时背景，已评审方案对SimHash等判断的纠偏优先于旧结论。

## 3. 架构与职责分层

![系统架构静态总览](design/system-architecture.svg)

Controller与校验层处理协议和参数；业务服务划分接收、查询、失效、领取、终态和检索；MyBatis Mapper负责显式SQL。向量器、codec、余弦和Top-K与Spring/持久化解耦，便于独立参考验证。

文档路径：`提交 → 两表短事务 → QUEUED扫描 → 有界执行器 → 条件领取 → CPU计算 → 终态短事务`。

搜索路径：`取得许可 → 查询向量化 → 候选快照 → 事务外评分与Top-K → 命中计数短事务 → 返回`。

Nginx承担HTTPS、整站入口认证和可信转发头处理；应用只监听回环。入口Basic Auth不是业务RBAC，H2 Console和管理入口不向公网开放。公开部署模板不是当前实机状态，发布事实看[测试与质量验证](testing/UI-RELEASE-verification.md)。

## 4. 确定性算法的具体约定

1. 保留原文，计算时依次NFKC、`Locale.ROOT`小写、Unicode空白折叠及去首尾空白；按code point处理，不按UTF-16单元切断emoji。拒绝孤立代理单元，原始和规范化长度分别受限。
2. 非空白字符产生`U:`前缀1-gram；相邻且不跨空白的字符产生`B:`前缀2-gram。标点作为普通非空白字符，同权重累计。
3. 每个特征固定执行32轮SHA-256；最终摘要首字节映射256桶，第二字节最低位决定正负。局部`long[256]`累计，不混入文档ID、时间、随机种子或全库统计。
4. 按固定下标顺序用double求范数、`StrictMath.sqrt`及归一化，再转float。零范数返回独立零数组；不共享可变摘要器或向量数组，不做并行浮点归约。
5. codec固定BIG_ENDIAN、256个有限float、1024字节。版本为`char12-sha256-r32-nfkc-root-ws-v1`；计算规则或轮数变化必须另换版本，不能静默混算旧向量。

余弦对零范数返回0，保留负分和零分并钳制到[-1,1]；分数不是概率。Top-K按分数降序、同分ASCII文档ID升序；堆头保存最差项，最终只排序K项，不以全量排序代替堆选择。

令特征出现次数为F、轮数R、维度D=256、候选数N。向量化约为`O(FR+D)`，评分与选择约为`O(ND+N log K+K log K)`。堆额外空间为`O(K)`；服务还持有候选向量及元信息，整体并非只有`O(K)`。5000份向量的原始字节为5,120,000B，不能把它当作含Java对象、前缀和JDBC开销的进程内存上限。

## 5. 接收事务、调度与所有权

### 提交锁为什么覆盖物理提交

如果锁只覆盖带`@Transactional`方法内部，代理可能在锁释放后才提交，最后容量名额、重复ID和两表可见性会出现窗口。实现用接收锁包住独立`TransactionTemplate`执行与返回，检查重复ID、总量和持久积压，再插入文档与QUEUED任务；物理提交完成才返回202。拒绝未知外层事务，不把回调结束误认为提交完成。

202只说明持久化接收，不表示向量化已完成。提交过程中无法确定commit结果时，按本次任务身份独立确认；无法确认则降级，不能盲目重插。

### 为什么不能把内存队列当可靠消息

Runnable仅携带taskId；数据库任务表保留QUEUED。扫描按稳定顺序小批补派，本地inFlight减少重复入队；队列满时清理本地标记、保留数据库事实，之后再扫描。总文档与待处理任务容量在接收事务中检查，和64个内存队列槽位是不同边界。

实际领取依赖`WHERE status='QUEUED'`条件更新，受影响一行后才拥有执行权，并持久化新的run_token、开始时间和尝试次数。inFlight不是跨执行者的正确性凭据。计算不长期持有数据库连接、行锁或事务。

## 6. 终态、失效与恢复

任务主状态为`QUEUED → RUNNING → SUCCEEDED / FAILED`。终态必须匹配RUNNING与run_token，迟到旧执行者不能覆盖新尝试。成功事务同时保存向量、算法版本、完成时间和任务成功；明确计算失败才持久化对应失败分类。不能把数据库暂时不可用或无法确认提交伪装为已经持久化的FAILED。

文档失效、向量就绪和任务状态分别表达检索资格、向量结果及处理过程。更新使用专门字段，任务完成不恢复已经失效的文档，也不覆盖hitCount。失效幂等保留首次时间；当前没有恢复有效或覆盖更新接口。

启动先拒接业务，确认旧进程退出、文件锁释放后恢复旧RUNNING为QUEUED；恢复事务提交后才READY和调度。成功、失败任务不因启动重做，原文、失效和计数保留。没有在线超时抢占或无限自动重试。

关闭先拒接、停派，再有界等待Worker并排空已进入的短数据库操作，最后关闭数据源。CPU不长期持有写屏障；超时计算不能在数据源关闭后回写，留下可恢复状态。30秒是Worker等待预算，不是永久卡住的数据库事务关闭承诺。真实SIGTERM曾暴露H2退出钩子抢先关库，已由Spring/Hikari统一负责正常关闭；该修复与独立SIGKILL恢复分别验证，不承诺断电安全。

## 7. 搜索快照与原子计数

先筛选：任务SUCCEEDED、向量存在且长度正确、文档未失效、文档和任务版本均匹配当前算法，以及可选渠道。读取候选快照后释放连接，再完成全部评分与Top-K，不长期持有事务等待CPU。

查询用`Semaphore.tryAcquire()`限流，默认仅1个搜索许可，繁忙明确429，不排无界等待。许可覆盖计算至计数物理提交，各退出路径释放。后台Worker数量和HTTP请求线程并发是不同概念。

选定最终命中后，将ID按固定顺序在同一短事务执行`hit_count=hit_count+1`，每行必须更新1行；任何一项失败整体回滚，不先读后改，也不对全部候选计数。

失效先提交、之后开始的搜索必须排除；重叠搜索允许返回其快照中的旧候选。计数阶段不重新筛掉刚失效的候选，避免已选中的命中漏计；只改hitCount，不复活文档。

计数commit后网络失败仍可能已计数。没有请求幂等标识，因此提交未知不能用当前累计值猜测，也不能重放增量。前后端均不自动重试搜索写入；GET诊断不计数。

## 8. 持久化、资源与安全取舍

H2 URL使用文件模式，`schema.sql`随JAR提供，Spring启动自动执行。表和索引使用`IF NOT EXISTS`，重复启动不清库；这不是自动迁移框架，不会自动修补任意旧表结构。

默认Worker=1、队列64、待处理上限1000、文档上限5000、搜索许可1、连接池最大4。单实例和永久锁、H2文件锁共同约束部署；版本切换不等于替换数据库。正常关闭后冷备，恢复验证使用独立副本，代码回退和数据恢复分别授权，不能覆盖正在写的生产文件。

浏览器写请求按实际scheme/host/port核对Origin。HTTPS代理配置曾独立复现协议识别不匹配，处理方式是明确的回环代理信任及入口覆盖转发头，不是全局信任客户端Forwarded。错误不返回SQL、堆栈或凭据；页面按纯文本呈现原文。
