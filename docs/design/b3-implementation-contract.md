## 范围与不变量

B3只补齐真实生产向量任务、终态、启动恢复和关闭。B1算法/版本/codec不改，DDL与六业务DTO不变，不实现B4检索或命中计数。单JVM、单H2文件，旧进程退出/文件锁释放后方可恢复；不启用AUTO_SERVER、不在线抢占超时任务。

1. 生产TaskExecutionHandler在事务外调用统一TextEmbedder，再通过独立短事务写终态；空文本零向量也成功就绪。任务版本不匹配应明确失败，不偷偷按新版本计算旧任务。
2. 成功事务先以RUNNING+run_token确认所有权，再写文档向量/版本/完成时间，和SUCCEEDED/finished_at同一物理提交；任一步受影响行数不对须回滚。Worker不更新invalidated、hit_count或原文。
3. 同token终态重放须幂等确认；旧token成功/失败都不能覆盖新尝试或文档，不能因旧回写被拒绝而把新任务标FAILED。
4. 非法输入、版本不匹配、计算异常有稳定脱敏错误分类（码≤64、消息≤512）；FAILED仅在可靠提交后成立。数据库无法记录终态不能伪造FAILED或仅日志后永久失联。
5. 明确回滚且可重试的DB故障有限重试，遵循现有最多3次/50、100ms起点；提交未知先新事务核对状态/token/向量一致性，不盲目再执行。无法确认则DEGRADED、拒接/停派、保留诊断和持久现场，后续按恢复流程重启。

## 启动、就绪、关闭

- readiness有明确RECOVERING/READY/DEGRADED/STOPPING/STOPPED等状态和单向边界；恢复初始拒接且不派发，不能先READY后查库。
- 旧RUNNING在启动短事务恢复QUEUED，清旧token与执行/终态时间及错误，保留attempt_count、提交时间、原文和失效/计数；QUEUED可补派，已成功/失败不重做。恢复提交成功后才放行，失败绝不READY。
- 业务API在恢复/停止门禁下实际拒绝请求，不仅健康页标未就绪。管理诊断读取的可用范围需明确；不能恢复中接受提交。健康对外不泄露SQL，任务READY不冒称B4/整个应用均完成。
- 关闭顺序：关闭新接收→停止扫描/派发→有界等待在途→确认不再有可进入的数据库回写→关闭数据源。保留QUEUED和未确认RUNNING供下次恢复。
- 超时仍在CPU中的计算不能在数据源销毁后写DB；应有受控终态写入许可/屏障，关闭许可后不再进入SQL，且等待已进入的短事务结束。不得用强制中断正在操作H2的线程掩盖生命周期问题。完整关闭/超时路径必须测试。
