# 文本向量化算法方案对比与选型报告

**项目：** Java 文本向量化与相似内容检索微服务  
**依据：**《Java 开发工程师笔试题—文本向量化与检索 v3.3》及《01-project-research.md》  
**版本：** V1.0 ｜ **日期：** 2026-10-22  
**文档属性：** 笔试技术选型 / 面试答辩材料

> **结论先行**：建议采用「Unicode 字符 1-gram + 2-gram → 带符号特征哈希 → 固定 256 维 float[] → L2 归一化 → 余弦相似度」，Top-K 使用容量为 K 的小顶堆。它更符合本题的**无模型、无训练、异步独立执行、固定维度、中文输入和可解释性**约束。它模拟的是**字面特征相似性**，不是语义 Embedding，不应声称理解同义词或上下文。

## 1. 研究目的与边界

这不是「哪个文本算法最先进」的开放式比较，而是**在笔试的明确限制下选择风险最低、效果可解释、可单独测试的模拟向量器**。算法必须与异步任务引擎相互独立：入库任务可在任意 Worker 执行；查询接口同步执行同一向量化算法；旧向量不应因为新增文档而悄悄变化。

| 约束维度 | 题目硬要求 | 设计含义 |
|---|---|---|
| 输出形态 | 固定 256 维 `float[]` | 不能只返回 64 位指纹、倒排列表或可变长稀疏词项 |
| 确定性 | 相同文本每次输出完全一致 | 固定预处理、哈希、权重、计算顺序和算法版本 |
| 空文本 | 输出全零向量 | 不能出现 NaN 或被错误拒绝 |
| 模型依赖 | 不调用 LLM / Embedding API | 使用纯本地计算；避免模型下载与外部服务 |
| 相似性 | 能模拟文本相似，不要求真正语义理解 | 相近字词/片段的文本应有可检验的相关性 |
| 工作方式 | 后台异步文档入库，前台同步检索 | 向量器必须可重入、线程安全、低状态依赖 |
| 技术环境 | Java 17+、Spring、H2 | 首版以标准 JDK、可审查的简单实现为优先 |

**先澄清两个概念：**「向量确定」只说明输出稳定；「语义相似」意味着不同表述但同一意图也能接近。前者本题必须满足，后者题目**不要求**。整段哈希能做到前者，却通常无法做到相近文本向量接近。

## 2. 候选方案与原理

### 2.1 A：整段文本 SHA-256 + 固定伪随机向量（对照基线）

把整段文本做 SHA-256，利用固定哈希派生 256 个数，再规范化。实现极简单、天然固定维度且确定，空文本可约定返回全零。但文本只修改一个字就会产生近乎无关的输出，因此无法稳定保留局部相似性。**适合作为反例基线，不建议交付为主算法。**

### 2.2 B：字符 Unigram/Bigram + 带符号特征哈希（首选）

先对文本作固定的 Unicode 规范化（如 NFKC、小写、空白合并），按 Unicode code point 生成单字符、相邻双字符特征。对每个特征计算固定哈希，映射到 256 个桶，并根据哈希中另一部分确定正负号，累计词频，再做 L2 归一化。

特点：不依赖词典和训练语料；单汉字、中文短句、英文、emoji 都可以处理；共享字符片段通常能贡献相似性；同一向量器可以在入库和查询端独立计算。代价是仅有 256 个桶，会发生碰撞，且无法学习「退款≈退钱」等语义关系。

> **重要区分**：带符号的 Feature Hashing 比「每个特征只加到正数桶里」更适合近似保持内积，但不能消除碰撞；更不能保证相似度分数严格非负。

### 2.3 C：纯字符 Unigram + 特征哈希（轻量替代）

每个单字符映射到固定桶，省去 bigram 生成。实现开销低、对字符集合重合敏感，中文短文本也容易实现。但丢失字符顺序，例如「设备离线故障处理」与「离线设备故障处理」在字符频率相同的情况下可能得到完全相同向量。适合作为性能/消融实验对照，不宜当作最终方案。

### 2.4 D：字符 Bigram/Trigram + 特征哈希（顺序敏感替代）

只使用长度为 2、3 的字符片段，对顺序和局部上下文更敏感；两段只有部分单字重合的文本可能被更好地区分。但单字符输入需要兜底策略，短中文句子改一两个字，得分可能显著下降。若笔试样本多为较长文本，它可以作为可切换实验配置，但默认未必优于 1+2 gram。

### 2.5 E：固定 256 词项词袋（BoW）/ TF（简单、可解释）

预先定义 256 个字/词槽位，文本出现某项就累计频次，得到 256 维数组。无须动态词表，也易于解释各维含义。但未知字词无法表达；中文需要确定分词或字符词项的规则；固定词表覆盖不足时，新增文档可能长期得到稀疏甚至零向量。适用于**领域词表稳定、可人工维护**的场景，通用笔试文本不推荐。

### 2.6 F：TF-IDF + 固定词表/降维（可扩展但维护重）

TF-IDF 利用词频（TF）及逆文档频率（IDF）降低常见词权重，有良好的经典信息检索解释。问题是：标准 TF-IDF 要从语料学习词表与 IDF；文档集合新增时权重可能变化，导致同一文本在不同时刻输出不同向量。要满足题目确定性，必须**冻结词表、IDF 和降维映射**，将其视为版本化模型，并设计更新时的历史向量重算机制。

结论：**可实现符合题意的工程版本，但实现/维护成本显著高于无状态特征哈希**。不能把未经冻结的动态 TF-IDF 直接放入本题异步服务。

### 2.7 G：SimHash 指纹（近重复检测有优势）

把文本特征加权后经多组符号投影，生成比特指纹，适合以汉明距离做近重复检测。传统场景常见的是固定长度 bit sketch，而本题接口明确是 256 维 float 数组及向量相似度。虽然能将 256 个 bit 转换成 256 个 ±1.0f，但那只是**指纹的浮点包装**，其自然相似性仍是汉明距离，不能直接等价于通常的浮点 Embedding。

结论：可用于近重复检测，作为面试对比有意义；为满足题面而包装成 float 会使方案显得绕远路。

### 2.8 H：MinHash / Jaccard（集合相似性，不优先）

将文本转成字符 n-gram 集合，MinHash 用多个固定随机置换签名估计 Jaccard 相似度，适合检测集合重合度。其自然输出是**整数签名**、自然比较方法是签名位相等比例，而不是余弦相似度。把 32/64 位整数直接转换为 `float` 可能丢失整数精度，甚至使签名相等性失真；要输出 256 维 float 需要额外编码设计。

结论：方案合理但**与本题接口和相似度习惯不契合**。除非明确要求重复检测，否则不推荐。

### 2.9 I：随机索引 / 固定随机投影（研究型备选）

给词项分配固定种子生成的稀疏随机向量，按词频累加为 256 维表示，理论上可无训练、固定维度。若仅为各 n-gram 分配固定随机方向，它与特征哈希同属相近的随机映射思路；若按上下文学习词项的分布表示，则必须管理语料统计和版本。对于本题，多了一层投影复杂度，工程价值不明显。

## 3. 统一对比矩阵

**评估口径：**「满足 256 float」指是否能够*自然地*表示为该结构；「稳态」指不用随着文档库增长重算同一段文本的向量；「文本相关性」仅是**字面相似性潜力**，不表示真实语义检索能力。下表为工程判断，不是外部测评数据。

| 算法 | 256 float 适配 | 无语料训练 | 新增文档时稳定 | 中文/短文本 | 典型局限 | 本题结论 |
|---|---|---|---|---|---|---|
| 整段 SHA 派生 | 自然 | 是 | 是 | 可处理 | 微小修改即随机变化 | 不选；反例 |
| 字符 1+2 gram + 签名哈希 | 自然 | 是 | 是 | 好 | 哈希碰撞、无同义词理解 | **首选** |
| 纯字符 1-gram 哈希 | 自然 | 是 | 是 | 好 | 忽略顺序、虚高匹配 | 备选对照 |
| 字符 2+3 gram 哈希 | 自然 | 是 | 是 | 短串较弱 | 对小幅修改过于敏感 | 候选对照 |
| 固定词表 BoW | 自然 | 需维护词表 | 是（词表冻结） | 取决于词表 | 未知词信息丢失 | 定制场景可用 |
| TF-IDF + 固定/降维 | 需设计 | **否** | 仅冻结后 | 依赖分词 | 重训与历史向量迁移 | 本题不优先 |
| SimHash | 需包装 | 是 | 是 | 取决于特征 | 原生是 bit 指纹 | 近重复适用 |
| MinHash | 需额外编码 | 是 | 是 | 依赖 n-gram | 原生是整数签名 | 不优先 |
| 固定随机索引 | 自然 | 可做到 | 是（固定投影） | 取决于特征 | 映射/计算更复杂 | 理论备选 |

**为何不把 BM25 放进主向量化候选？** BM25 是基于词项统计的经典检索打分方法，并不直接产生本题指定的、可以存储和复用的 256 维文档 `float[]`；它适合在更完整的搜索系统里与向量检索并列成为词法召回策略，但不能直接替换这个向量接口。

## 4. 探索性样本实验：有比较，但不夸大

为避免只凭经验下结论，采用**Python 标准库原型**对 5 种代表性配置做了一个很小的定性对比：字符 1+2 gram 签名哈希、字符 2+3 gram 签名哈希、纯 1-gram 签名哈希、256 bit SimHash 转 ±1 浮点、整段 SHA 派生随机向量。统一输出 256 维并用余弦相似度比较；特征哈希原型使用**固定 BLAKE2b 派生桶位/符号**，SimHash 使用固定 SHA-256 位投影。

**请注意实验边界：** 这是 8 组人工文本的*探索性*比较，非公开基准数据集，也非最终 Java 实现；分数依赖哈希规则、预处理和样本选择，**不能解释成准确率、召回率或算法普遍优劣证明**。后续 Java 版若改用 SHA-256、Murmur3 或不同 normalization，数值可能变化；正式比较需固定同一套测试语料、哈希实现和实验环境。

| 文本关系（人工构造） | 1+2 gram 签名哈希 | 2+3 gram 签名哈希 | SimHash→±1 cosine | 整段 SHA 派生 |
|---|---:|---:|---:|---:|
| 完全相同文本 | 1.0000 | 1.0000 | 1.0000 | 1.0000 |
| 「押金退款规则」与「押金退还规则」 | 0.8696 | 0.6842 | 0.6562 | -0.0156 |
| 「结算流程」与「结算流程说明」 | 0.8997 | 0.8885 | 0.7344 | -0.0156 |
| 「设备离线故障处理」与「离线设备故障处理」 | 0.8462 | 0.5017 | 0.6875 | -0.0469 |
| 「怎样退钱」与「如何申请退款」 | 0.1048 | 0.0000 | 0.0078 | 0.0234 |
| 「分润结算流程」与「设备离线故障处理」 | 0.0673 | -0.0716 | -0.0469 | 0.0469 |

上表前四类说明：字符级特征在本组样例中保留了“相同、局部改写、包含和局部重排”的关联；整段哈希没有这一性质。第五行说明**任何上述纯字面方法都没有真正理解同义词**。另一个提示是，纯 1-gram 对字符重排样例可达到 1.0000，显示其完全忽略顺序的弱点。

**可复现实验口径：** Python 3 标准库（`hashlib`/`unicodedata`/`collections`），NFKC、小写、空白规范化，固定 256 维；实验结果仅作为本报告的预研证据，正式代码验收以 Java 17 版单元测试为准。未进行 Java CPU 基准、压力测试或真实语义检索评测。

## 5. 最终推荐与工程实现约定

### 5.1 推荐算法流程

```text
原始文本（保留入库，用于详情和溯源）
    ↓ 固定预处理：NFKC / Locale.ROOT 小写 / 空白规范化
Unicode code point 序列
    ↓ 提取前缀区分的 1-gram、2-gram；短文本至少保留 1-gram
特征频次（按稳定顺序处理）
    ↓ 固定哈希：桶下标 0..255 + 正负符号
256 维整数累计（避免浮点并行归约不确定性）
    ↓ 转 float + L2 归一化（固定求和顺序）
float[256]；空文本 = 256 个 0.0f
    ↓ 与同版本文档向量计算余弦相似度
按 score 降序，documentId 升序做 Top-K
```

**实现细节必须写死并版本化：** `embeddingVersion`；Unicode 规范化规则；大小写/空白规则；token 边界策略；n-gram 范围与权重；哈希算法、字节序和负号位；累加精度与归一化顺序。不要在同一算法版本中悄悄修改其中任何一项。

- Java 17 首版优先选 **SHA-256（标准 JDK）** 或已允许的基础工具包所支持的固定哈希，避免依赖非固定随机种子；实验原型中的 BLAKE2b 仅用于对比，不能将其数值直接当成 Java 结果。
- 使用 `String.codePoints()` 而不是 `char` 循环，以避免拆开 emoji 等代理对；如需防过载，限制 code point 数量。
- 特征命名加入 `U:`/`B:` 前缀或长度编码，避免同样的字符串来自不同 n-gram 类型时产生意外混淆。
- 单线程按固定索引归一化，单位向量用 `double` 做范数累计；最终写入 `float[]`，并做有限数值校验。
- H2 保存 256×4=**1024 字节原始 float**（约 1 KiB，不含其他字段），编码字节序固定；切勿使用 Java 原生对象序列化。
- 对零向量与零向量/非零向量的余弦相似度统一定义为 0，避免除零与 NaN；相同文本、并发调用及重启后的向量按位一致。

### 5.2 CPU 耗时模拟与检索的一致性

题目既要求后台向量化模拟 CPU 耗时，又要求检索接口同步使用“相同的向量化逻辑”。因此**不能通过向量化服务偷偷切换两套算法**：文档向量与查询向量必须具备相同规则和版本。

可在算法之前或算法中加入**配置化、可重复的真实计算负载**（例如固定轮数摘要计算且结果参与确定性计算），但不把 `Thread.sleep()` 当作 CPU 密集计算。CPU 轮数与文本长度均需限制；否则后台 Worker 与同步查询线程争用 CPU，反而使检索不可用。此处设计为可测试参数，最终值待运行实验决定。

### 5.3 为什么不用真正的 Embedding 模型

并不是说模型效果不如特征哈希，而是题面明确**不调用 Embedding API**、强调工程实现。模型会引入下载、模型格式、推理依赖、部署资源及维度适配等额外工作，偏离考核目标。实际生产 RAG 的语义查询仍通常需要合适的文本嵌入模型。

## 6. 候选算法的评分说明（主观决策，不等于跑分）

采用 1–5 分的专家评审量表，权重为：硬约束适配 25%、无状态与增量稳定 20%、中文短文本字面相似能力 30%、实现和测试成本 15%、维护可解释性 10%。评分只是**选型会议的讨论辅助**，不是实验结果。完整说明如下。

| 候选 | 约束适配/5 | 无状态稳定/5 | 字面近似/5 | 低实施成本/5 | 可维护/5 | 加权参考/5 |
|---|---:|---:|---:|---:|---:|---:|
| 1+2 gram + 签名哈希 | 5 | 5 | 4 | 4 | 4 | **4.45** |
| 纯 1-gram 哈希 | 5 | 5 | 2 | 5 | 4 | 4.00 |
| 2+3 gram 哈希 | 5 | 5 | 3 | 4 | 4 | 4.15 |
| 整段 SHA 派生 | 5 | 5 | 1 | 5 | 5 | 3.80 |
| 固定词表 BoW | 4 | 4 | 3 | 3 | 3 | 3.45 |
| 冻结 TF-IDF + 降维 | 3 | 2 | 4 | 2 | 3 | 2.95 |
| SimHash→float | 3 | 5 | 3 | 3 | 3 | 3.40 |
| MinHash→float | 2 | 5 | 3 | 2 | 3 | 3.00 |

**评分解释：** 任何高分算法也不能取代硬性约束；整段 SHA 在工程实现容易性上表现良好，但在题目要求的文本相似性上明显不及首选。上表评分依赖权重及个人判断，不应单独用“4.45”声称科学优越性。

## 7. 验收用例、风险与面试答辩

### 7.1 算法验收用例

| 验收类别 | 断言/目标 |
|---|---|
| 维度与类型 | 返回 256 维 `float[]`；正常非空文本为有限值 |
| 严格确定性 | 相同输入重复 100 次、多线程并发、重启后的 256 元素逐位相等 |
| 空输入 | `""` 及按约定归一化后为空的纯空白文本输出全零 |
| 字符兼容 | 单字、英文大小写、中文标点、emoji、组合字符、超长文本均有明确行为 |
| 局部相似 | 选定人工样例中，相同/少量扩充的文本应相对更近；不对所有文本作全称保证 |
| 哈希碰撞 | 针对碰撞构造样例，记录影响，但不承诺 256 维完全无碰撞 |
| 数值稳定 | 向量编解码 round-trip 位一致；余弦分数不出现 NaN/Infinity |
| 索引版本 | 只比较 embeddingVersion 一致的向量；升级必须重算或隔离旧向量 |
| 检索排序 | 同分 documentId 升序、Top-K 与全量排序参考实现一致 |

### 7.2 主要风险及应对

1. **错误把字面相似包装成“语义理解”**：README、接口文档和面试话术明确限定模拟能力。
2. **不同计算路径结果不一致**：入库和查询共享同一 `EmbeddingService` 实现，固定版本与测试。
3. **哈希冲突导致排序反常**：采用带符号映射；留固定样本测试，文档解释 256 维限制；不要承诺无误差。
4. **归一化引起输入语义损失**：保留原始文本；把规范化视为显式版本化规则。
5. **CPU 模拟过重**：有界轮数、队列背压、按环境基准调参；检索时延必须实测。
6. **把排序优化误写成内存 O(K)**：堆自身 O(K)，若加载 N 条向量，总候选内存仍是 O(N×256)。

### 7.3 面试时建议的三段式回答

**为什么选它？** 因为题目要求的是无需外部模型、固定 256 维、无状态和可重复的模拟向量化，不是真实语义编码；字符 n-gram 保留局部字面特征，哈希省去词表训练，适合多线程异步独立计算。

**你比较过什么？** 对比了整段哈希、不同 n-gram、固定 BoW、TF-IDF、SimHash、MinHash 和随机投影；还用极小样本做了探索性数值对比，但明确不把它当成正式算法准确率结论。

**它不足在哪里？** 中文同义词、同义改写、否定关系和深层语义无法保证；256 维哈希存在碰撞。未来真实业务可在不改变异步任务/文档管理主体的前提下，将向量器实现替换成真实 Embedding 模型，并通过 embeddingVersion 管理迁移。
