# AI 知识库文本向量化与相似内容检索业务说明书

**项目：** Java 文本向量化与检索微服务  
**依据：**《Java 开发工程师笔试题—文本向量化与检索 v3.3》及《01-project-research.md》  
**版本：** V1.0 ｜ **日期：** 2026-10-22  
**文档属性：** 业务背景、功能范围、业务流程与总体解题思路

> **项目定位**：为 AI 知识库提供一项基础的检索服务——接收原始文档，后台异步生成固定维度的模拟文本向量，持久化保存；接收用户查询，计算相似度并返回 Top-K 相关文档，同时提供文档状态、来源和命中统计管理。它是**知识检索基础组件**，不是完整的 AI 聊天系统。

## 1. 项目背景：为什么需要它

### 1.1 企业知识从“能存”走向“能找”

企业的操作手册、FAQ、业务制度、工单记录和产品文档会不断增加。即使所有文档都已经存入数据库，用户也可能因为不知道精确关键词、表达习惯不同或描述不完整，难以快速定位相关资料。

例如在一套共享充电宝 SaaS 系统里，知识库可能包含：「押金退还规则」「订单退款处理说明」「设备离线排查」「代理商结算手册」。客服输入“充电宝归还之后押金怎么退”，希望看到与退款相关的文档，而不是单纯按文档上传时间展示列表。

**注意：以上共享充电宝业务只是便于理解的演示场景，并不代表本次招聘公司已经提供了这套产品或真实数据。**

### 1.2 从关键词匹配到文本相似性检索

传统 `LIKE` 查询通常依赖字面匹配。相似度检索引入另一条路径：将文档和查询都表示为同维度的数字向量，再通过相似度函数对候选文档排序。

真正的 Embedding 模型可以学习语义关系，但本题明确不调用 LLM/Embedding API。因此本次实现使用**本地模拟向量器**保留部分字符/文本片段相似性：让相同或局部改写的文本倾向于接近，而不是保证“退款”和“退钱”等不同表达具有真实语义联系。

### 1.3 对业务系统意味着什么

- **对知识维护人员**：可以提交原始文档、跟踪向量化任务、查看完成状态和失效情况。
- **对搜索调用方**：可以给出文本、topK 和可选渠道条件，立即获得相关文档的排序结果。
- **对管理员/运营人员**：可以追溯文档来源、入库和向量完成时间、命中次数，剔除过时文档。
- **对未来 AI 问答系统**：本服务可以先找出候选知识，再由上层系统决定是否把这些结果交给大语言模型生成回答。

## 2. 项目目标与成功标准

### 2.1 核心目标

构建一个**单进程、可直接启动的 Java 微服务**，覆盖从文档接收到异步向量化、H2 文件持久化、同步 Top-K 检索、文档生命周期管理的完整闭环，并能通过可重复的测试证明并发安全。

### 2.2 项目不做什么

本次**不开发**：实际 LLM/Embedding 接口、真实语义理解、PDF/Word 自动解析、长文档切片、多租户权限体系、前端聊天页面、向量数据库、消息中间件、分布式任务调度、多实例部署。未来扩展可以讨论，但不应成为笔试首版依赖。

### 2.3 建议验收目标

| 目标 | 可以直接观察的验收结果 |
|---|---|
| 异步接收 | 提交文档后先返回任务 ID，不等待向量化完成 |
| 向量确定 | 同一文本生成的 256 维 `float[]` 完全一致；空文本为全零 |
| 任务可查 | 可查询排队、处理、完成、失败以及相关文档信息 |
| 检索正确 | 仅检索向量就绪且有效的文档，支持渠道筛选，返回 Top-K 降序 |
| 信息可追溯 | 保存渠道、提交/完成时间、命中次数，并支持查询 |
| 数据可恢复 | 服务正常重启后 H2 文档与元数据保留；遗留未完成任务可被恢复调度 |
| 并发不出错 | 同一任务不被重复领取成功、失效不被覆盖、命中次数不丢失 |

其中“启动后恢复处理中任务”是工程建议，超出了 PDF 对任务恢复的直接文字要求，但符合文件持久化和可靠异步处理的整体目标。

## 3. 主要业务对象与业务规则

### 3.1 三类核心对象

| 业务对象 | 包含什么 | 为什么要存在 |
|---|---|---|
| 文档 Document | documentId、原文、渠道、有效状态、时间戳、向量、命中次数 | 可检索的知识与元数据载体 |
| 向量化任务 EmbeddingTask | taskId、documentId、状态、执行时间、错误原因 | 把耗 CPU 的工作从提交请求分离出去 |
| 检索请求 SearchQuery | 文本、topK、可选 channel | 定义要找什么以及返回多少条 |

**渠道 channel** 可以理解为业务来源或隔离标签，如 `faq`、`operation`、`customer-service`，未传默认 `default`。它不是用户权限控制，也不是完整的多租户授权模型。

### 3.2 建议统一的边界规则

题目未详述所有边界。为减少开发分歧，第一版建议固定以下约定，作为设计决定而非题面原文：

- 重复 `documentId` 返回 409，不覆盖旧文档；空文档 ID 返回 400。
- `text=null` 为参数错误；`text=""` 合法，产生零向量；原文保持不变以供溯源。
- `topK` 必须为正整数且有上限；无匹配文档返回空数组。
- 文档失效为幂等操作，重复失效保留首次时间；首版不提供恢复有效操作。
- 只有最终 Top-K 返回结果更新命中计数；命中指“被检索结果返回”，不等于真实点击或阅读。
- 异步任务成功不等于文档始终有效：失效标记与向量就绪状态是两个独立维度。

## 4. 功能清单：系统具体实现什么

### F01 文档提交与异步入库

上游发送文档 ID、原始文本及可选渠道。服务先校验参数并在 H2 中持久化文档记录与 `QUEUED` 任务，然后立即返回 `taskId`（建议 HTTP 202）；后台 Worker 再执行耗时的模拟向量化。

**业务价值**：避免上传接口长期阻塞，便于批量文档处理和任务追踪。

**特别约束**：任务尚未成功完成时，文档即使已经入库，也不能参与检索。

### F02 文本模拟向量化

统一使用确定性本地算法，将任意合法文本转换为 256 维 `float[]`。同一个文本在多次调用、不同线程和重启之后，应得到完全一致的向量；空文本全零；不调用任何在线模型。

**业务价值**：为相似度检索生成可比较的数字特征。**能力边界**：本次实现字面相似性的模拟，不保证语义理解。

### F03 任务状态查询

允许按 `taskId` 查询 `QUEUED（排队）/ RUNNING（处理中）/ SUCCEEDED（完成）/ FAILED（失败）`，任务完成后可看到对应文档和向量是否就绪；失败任务能查到原因。

**业务价值**：调用方无需一直等待，也不会混淆“已经接收”和“已经处理完成”。

### F04 同步相似内容检索

用户提交查询文本、正整数 `topK` 和可选渠道。服务使用**与入库一致的算法**生成查询向量；筛选有效、已完成且同版本的候选文档，计算余弦相似度，按相似度降序返回前 K 条。

**业务价值**：在文档库中找到与当前描述字面特征较接近的知识项；用户无需知道精确文档 ID。

### F05 文档查询与失效管理

提供文档分页列表、详情、任务关联状态、向量是否就绪、提交/完成时间与渠道信息；支持主动标记文档失效，失效后不再参与新的检索。

**业务价值**：让知识维护人员可以管理过期资料，也能排查“为什么搜不到”的问题。

### F06 来源追溯与检索统计

记录渠道、提交时间、向量化完成时间、命中次数。每次成功返回检索结果时，对最终命中的文档计数，采用数据库原子增量防止并发丢失更新。

**业务价值**：支持基础的知识来源核对和检索活跃度观察。注意命中次数不是点击量，更不是答案正确率。

## 5. 全流程设计：两条主业务链路

### 5.1 链路 A：知识入库（异步）

```text
提交文档 → 参数校验 → H2短事务保存 Document + QUEUED Task → 返回taskId
                       ↓
调度器扫描QUEUED → Java有界队列 → Worker条件领取 (RUNNING)
                       ↓
         事务外CPU向量化计算
                       ↓
      成功：向量+完成时间+SUCCEEDED（同事务）
      失败：FAILED+错误原因（落库）
```

**为什么要数据库和 Java 队列同时存在？** H2 是已接收任务的可靠记录；内存队列仅负责当前进程中的执行调度。仅依赖内存队列，一旦进程崩溃，排队任务就会消失。重启时可以从 H2 中恢复未完成工作。该实现定位于单实例，不声称已具备多实例分布式调度能力。

### 5.2 链路 B：用户检索（同步）

```text
查询请求(text/topK/channel) → 用同版本算法生成查询向量
                       ↓
 H2筛选有效+就绪+渠道匹配 → 余弦相似度评分
                       ↓
    PriorityQueue维护Top-K并稳定排序
                       ↓
     原子增加最终命中数 → 同步返回结果
```

检索是同步接口，因而查询文本向量化会占用当前请求的 CPU 时间，必须设置文本长度和计算负载上限。Top-K 的小顶堆减少排序开销，但不意味着读取大量文档向量没有内存成本。

## 6. 关键架构与解题思路

### 6.1 总体方案：简单单体服务，职责清晰

采用 Java 17 + Spring Boot + MyBatis + H2 文件模式。服务按职责划分：`api` 负责协议与校验、`document` 负责文档生命周期、`task` 负责持久任务和线程池、`embedding` 负责确定性算法、`search` 负责余弦相似度与 Top-K、`persistence` 负责 H2 读写。

**为什么不引入 RabbitMQ、Redis、向量数据库？** 题目要求队列自行通过 Java 实现，数据存储指定 H2；引入中间件既违反/偏离约束，也会掩盖对 Java 队列和并发基础的考察。

### 6.2 模拟向量算法：不训练、不外调、可重复

建议：Unicode 字符 1-gram + 2-gram，利用固定哈希映射到 256 维的正负桶中累计，再做 L2 归一化。检索使用余弦相似度；相同文本结果严格相同，局部文字重叠通常产生一定相似性。

**为什么不是整段 SHA？** 整段 SHA 虽然稳定，但修改一个字之后，输出几乎随机变化，难以体现局部文本相似。**为什么不是动态 TF-IDF？** 它依赖语料统计，若随新增文档重新训练，可能改变同一文本输出，不适合这道题无需维护模型版本的初版方案。

### 6.3 异步任务可靠性：以数据库状态为准

Worker 领取任务时使用条件更新，只有 `QUEUED -> RUNNING` 成功者才能处理，避免重复领取；计算过程在事务外完成；结果写入、完成时间与任务成功状态在同一短事务中落库。调度器扫描 `QUEUED` 任务而非只依赖提交时内存入队，避免事务提交后、入队前宕机造成丢任务。

初版重启时将遗留 `RUNNING` 恢复为 `QUEUED` 再调度；计算可能重复执行，但成功写入通过状态条件和事务确保一致。这属于**至少执行一次计算、幂等结果提交**的思路，而非“计算恰好一次”。

### 6.4 检索结果与失效并发

失效状态单独维护，向量 Worker 完成时不得覆盖它。并发检索与失效的默认约定为**查询候选快照语义**：失效完成后新发起的检索不再包含文档；与失效重叠的在途请求可能返回先前读到的有效候选。这是明确的业务语义，不是漏洞修饰。

### 6.5 命中计数与来源管理

检索只统计最终 Top-K 结果，使用 `UPDATE ... SET hit_count = hit_count + 1` 实现数据库原子累加，避免读改写丢失更新。业务来源保留 `channel`，时间统一使用可跨时区解释的格式；文档列表默认不下发 1024 字节向量载荷。

## 7. 核心接口（建议定义）

| 方法与路径 | 功能 | 关键输入/输出 |
|---|---|---|
| `POST /api/documents` | 提交文档 | documentId、text、channel? → 202 + taskId |
| `GET /api/tasks/{taskId}` | 任务详情 | 状态、开始/完成时间、错误原因、关联文档 |
| `GET /api/documents` | 文档列表 | 分页、渠道/失效筛选、基础元信息 |
| `GET /api/documents/{documentId}` | 文档详情 | 原文、来源、向量就绪、状态、命中次数 |
| `PUT /api/documents/{documentId}/invalidation` | 文档失效 | 幂等成功，重复操作不修改首次失效时间 |
| `POST /api/search` | 向量检索 | text、topK、channel? → 排序结果及相似度 |

以上 URL、HTTP 状态码、去重规则属于**设计建议**；题目规定的是能力而不是固定 REST 路由。实现与 README/测试约定应一致。

## 8. 示例：一个真实可讲清楚的业务故事

**假设场景**：客服部门准备把三篇内部 FAQ 导入知识库。

| 文档 ID | 标题（用作示例文本描述） | 渠道 |
|---|---|---|
| DOC-001 | 共享充电宝押金退款规则 | faq |
| DOC-002 | 共享充电宝押金退还操作说明 | faq |
| DOC-003 | 设备离线故障处理方法 | operation |

**操作一：入库。** 运营提交 DOC-001、DOC-002、DOC-003；系统依次返回任务 ID，不要求调用方等待 CPU 计算。通过任务查询，确认状态从排队进入处理，再进入成功。

**操作二：检索。** 客服输入“共享充电宝押金退款”，并设置 `topK=2`、`channel=faq`；系统同步完成查询向量计算，只在有效、已完成的 `faq` 文档中取相似度前两篇。最终排名由运行中的算法确定，不能预先编造固定分数。

**操作三：知识失效。** DOC-001 的规则已过时，运营将其标记失效。失效后新发起的同样检索不再返回 DOC-001；文档详情仍保留其历史来源和任务信息。

**操作四：统计与重启。** 检查最终结果的命中数是否累计，重启服务后再次查看：文档、失效状态、任务与命中统计仍然存在。这些行为证明系统不仅能“搜出来”，还具备基础管理与可靠性。

## 9. 数据模型、非功能要求与验收

### 9.1 推荐数据模型

`documents`：`document_id`、`raw_text`、`channel`、`submitted_at`、`vector_completed_at`、`invalidated`、`invalidated_at`、`vector_bytes`、`embedding_version`、`hit_count`。

`embedding_tasks`：`task_id`、`document_id`、`status`、`submitted_at`、`started_at`、`finished_at`、`error_code`、`error_message`。

256 个 `float` 按固定字节序编码后为 1024 字节；H2 使用文件持久化，启动时运行幂等 DDL。文档记录和任务记录要能关联，向量与任务成功状态需要在同一提交点一致可见。

### 9.2 非功能要求

- **可靠性**：任务已接收的定义是数据库事务已提交；恢复不应依赖内存队列。
- **并发安全**：线程池有界、任务领取条件更新、失效互不覆盖、计数原子自增。
- **可维护性**：算法版本、错误码、队列容量和文本长度限制明确可查。
- **可验证性**：单元测试覆盖算法；集成测试覆盖异步、失效并发、计数并发与文件持久化。
- **安全与边界**：限制输入长度、分页大小、topK 和积压任务数；避免无界队列与无限制 CPU 负载。

### 9.3 关键验收演示

1. 提交文档后马上拿到 taskId；人为阻塞 Worker 时文档不能被搜索到。
2. 相同文本重复调用得到逐位一致的 256 维向量；空文本全零。
3. 对相似查询返回排序稳定的 Top-K，支持渠道筛选和失效过滤。
4. 100 个并发成功检索对同一最终返回文档计数无丢失更新。
5. 一边向量化、一边将该文档标记失效，完成后仍然失效。
6. 正常重启后数据与计数保留，遗留任务有明确恢复路径。

## 10. 项目实施思路与工作量

**建议里程碑：** M0 项目和 H2；M1 确定性算法；M2 异步任务及查询；M3 检索、失效与统计；M4 并发/恢复测试；M5 文档、Git、AI 对话记录与交付检查。

| 交付层次 | 有效工时估算（使用 AI 辅助开发） | 包含什么 |
|---|---:|---|
| 可演示 MVP | 6–10 小时 | 核心接口、基础算法和主流程 |
| 推荐交付版 | 12–16 小时 | 完整功能、主要异常、关键测试、文档与 Git |

以上是**估算而非承诺**，以环境依赖、测试问题和实际代码质量为准。题目本身写明“没有时间要求”，如果只有一天开发时间，应优先确保可运行闭环和关键测试，服务器部署属于加分项，可以后置。

## 11. 与未来完整 RAG 系统的关系

完整 RAG（Retrieval-Augmented Generation）通常会有：文档获取/解析 → 切片 → 真正的 Embedding → 索引/检索 → 相关片段组装 → 调用大语言模型生成答案。**本次笔试只覆盖其中“文本向量化、存储、检索与基础管理”的简化环节**，没有做文档解析、切片、模型调用和答案生成。

未来若需要真正的语义检索，可以在保留文档管理、任务队列、任务状态与统计框架的同时，替换/扩展向量化实现并迁移历史向量。需要注意：实际生产使用的维度可能不再是 256，届时数据模型和查询策略也要同步演进。

## 12. 面试时可以怎样介绍这个项目

> **30 秒业务介绍**：这是一个面向 AI 知识库的文本检索基础服务。业务方异步提交知识文档，系统在后台生成模拟文本向量并保存；搜索时把查询文本转成同维度向量，通过余弦相似度返回 Top-K 文档。同时提供文档失效、来源追踪和检索命中统计。它不直接生成 AI 答案。
>
> 
> **60 秒技术介绍**：技术上我采用 Java 17、Spring Boot、MyBatis 和 H2 文件数据库。H2 记录任务状态，Java 有界队列执行 CPU 模拟向量化；Worker 通过条件更新防重复领取，计算在事务外，结果与任务完成状态在短事务中一致提交。算法选用字符 n-gram 特征哈希输出固定 256 维向量，同步检索通过余弦相似度和小顶堆返回 Top-K。对失效并发和检索命中计数，分别使用独立字段更新与数据库原子累加，并通过测试验证。

## 14. 附录：建议的接口演示样例

以下报文仅作为开发和面试演示约定，**不是题目给出的固定协议**；真实字段名称及返回结构以最终实现和 OpenAPI/README 为准。

**提交文档**：`POST /api/documents`

```json
{"documentId":"DOC-001","text":"共享充电宝押金退款规则","channel":"faq"}
```

返回 `202 Accepted`，示例：

```json
{"taskId":"<server-generated-id>","status":"QUEUED"}
```

**检索文档**：`POST /api/search`

```json
{"text":"充电宝押金退款","topK":2,"channel":"faq"}
```

响应至少能够说明“返回的文档是谁、为什么入选（score）、来自哪个渠道”。不要在说明书中提前写死具体相似度，因为分数取决于已经固定的向量算法及当前入库样本。

**演示准备清单**：启动项目、清洁数据目录、提交 3 篇样例文档、轮询任务、检索、标记失效、再次检索、重启并查看元数据；最后执行并发和确定性测试。若测试环境不能显示 QUEUED/RUNNING 的瞬时状态，可在集成测试中采用可控的 Worker 阻塞点证明异步行为。
