> **文档用途**：提供给 Pro 推理模型作为独立业务与工程分析的输入材料；不是已经验收的 PRD，也不是最终技术方案。  
> **项目性质**：Java 中高级后端工程师招聘笔试；AI 应用方向，单机微服务原型。  
> **版本 / 日期**：V1.0 / 2026-10-22  
> **权威来源**：《Java 开发工程师笔试题-文本向量化与检索-v3.3.pdf》。其余材料为候选人的前期理解、调研与设计建议。

## 1. 项目背景与业务价值

企业知识可能分散在 FAQ、操作手册、技术文档、业务规则与历史处理记录中。传统关键词搜索通常依赖精确或部分字面匹配，不利于用户在描述与文档标题不一致的情况下快速定位可能相关的内容。一种可扩展的知识检索思路，是将文本转换成定长向量，使用相似度算法对候选文档评分，再按相关性排序返回。

在真实 AI 知识库系统里，这一能力可作为 **检索组件**：知识文档先被索引，用户输入自然语言问题时先检索相关材料，再由上层应用显示文档，或进一步交给大语言模型生成答案（RAG 等架构）。**本笔试仅实现模拟向量化与检索微服务，不要求生成 AI 答案。**

**示例业务（仅为说明场景，非招聘公司披露的真实业务）**：假设知识库已有「充电宝押金退还规则」「订单退款操作说明」「代理商结算流程」「设备离线排查手册」。客服输入“归还充电宝后押金怎么处理”，系统应返回更可能相关的若干文档，并可查到来源渠道、任务状态和命中次数。由于笔试不使用真实 Embedding 模型，所谓“更相关”主要是模拟算法捕获的 **字符/词片段相似性**，不能保证识别所有同义词、语义近义或自然语言意图。

### 1.1 业务使用者与核心诉求

| 使用者/调用方 | 目的 | 典型动作 |
|---|---|---|
| 知识维护系统 / 文档提交方 | 文档持续进入知识库，不阻塞提交请求 | 提交文档、获取任务 ID、查询处理进度 |
| 搜索调用方 / 客服 / 上层 AI 应用 | 根据自然语言描述获取相关候选 | 传文本、topK、可选渠道，获取排名结果 |
| 知识运营或维护人员 | 管理过时信息并追溯结果来源 | 查看文档列表详情、标记失效、查看命中数 |
| 后台系统运维与开发人员 | 保证高并发与异常情况下服务可靠 | 观察失败状态、排队情况，复现测试与恢复 |

### 1.2 业务目标及非目标

- **业务目标**：文档先入库并异步生成模拟向量；只有计算完成且有效的文档才能参与同步 Top-K 检索；可查询状态与来源，并维护基础命中统计。
- **工程目标**：在题目给定技术限制内，构建可启动、持久化、并发安全、可测试、可解释的 Java 项目，能够应对面试对设计和代码的深挖。
- **非目标**：不调用真实 LLM 或 Embedding API；不建设聊天机器人、完整 RAG 编排、权限/多租户体系、文件解析、文档切块、线上向量数据库、RabbitMQ/Kafka 等外部队列、多节点调度、前端管理页面。

## 2. PDF 已明确的硬性需求（不得擅自改变）

### 2.1 六项核心业务能力

| ID | 业务功能 | 必要行为 |
|---|---|---|
| F01 | 提交文档任务 | 接收 documentId、原始文本、可选渠道；快速返回 taskId；后台队列异步向量化；未完成不得参与检索 |
| F02 | 本地模拟向量化 | 输出固定 256 维 `float[]`；相同文本向量完全一致；空文本产生零向量；不调用外部模型服务 |
| F03 | 任务状态查询 | 根据 taskId 查询排队中、处理中、完成、失败；完成后可取得文档信息 |
| F04 | 同步 Top-N / Top-K 检索 | 查询文本使用同一向量化逻辑；在有效且已完成文档中计算相似度、降序取前 K；可按渠道过滤 |
| F05 | 文档生命周期管理 | 支持主动标记失效；失效后不参与检索；列表和详情包含提交时间、完成时间、就绪状态、失效状态等 |
| F06 | 来源溯源与命中统计 | 渠道不传为 `default`；记录提交时间、向量完成时间、检索命中次数；检索更新计数 |

### 2.2 明确技术限制与交付要求

1. **Java 17 及以上 + Spring**；可以使用基本工具包。
2. **H2 嵌入式数据库**；JPA 或 MyBatis 均可；必须使用 **文件持久化模式**；提供 DDL 且项目启动自动建表。
3. **Java 原生实现队列**，不得引入消息队列中间件。
4. **使用 AI 作答**；项目需保留关键 AI 对话及真实 Git 迭代提交时间线。
5. 提交可直接启动的完整项目；Git 仓库地址或干净源码压缩包；不应把编译产物、日志打进压缩包。
6. 题目写明 **“没有时间要求，自由发挥即可”**；代码可读性、设计文档、单元测试、自有服务器部署属于加分项，非全部硬性要求。
7. 题目特别声明：模拟向量化不必具有真实语义理解，主要关注文本向量化的异步工程实现；后续面试会深入追问。

## 3. 主要业务流程与边界

### 3.1 文档入库：异步链路

```text
调用方提交文档（ID / 原文 / 可选渠道）
 → 参数验证
 → 持久化文档与排队任务（尚无可检索向量）
 → 返回 taskId
 → Java 内存队列 / Worker 后台计算
 → 向量化成功：原文关联 256 维向量、记录完成时间、任务置完成
 → 向量化失败：记录任务失败及可诊断信息
```

**业务关注点**：提交成功不等于向量化成功；任务状态与文档是否可检索不能混淆；CPU 耗时不能落到提交接口中同步执行；任务执行中服务异常如何保证已接收任务有明确去向。

### 3.2 文本检索：同步链路

```text
调用方提交查询（查询文本 / topK / 可选渠道）
 → 使用与入库一致的本地算法计算查询向量
 → 筛选已就绪、未失效、渠道符合条件的文档
 → 计算相似度 → 降序取 Top-K → 更新最终命中文档的统计
 → 同步返回检索结果及必要来源信息
```

**业务关注点**：过滤发生在 Top-K 选择之前；命中指进入检索返回结果而非用户点击；同分排序需明确；空文本零向量和 `topK` 边界必须有可解释的处理规则。

### 3.3 文档失效与任务状态是两个独立概念

文档在向量化期间可能被主动失效。即使任务随后完成，文档也不能重新进入有效检索结果。一个合理业务状态是 **“任务已完成 + 文档已失效”**，并非矛盾。检索与失效同时进行时，是否采用查询快照语义或强一致二次校验，需显式定义并验证。

## 4. 必须由深入分析回答的业务与技术问题

### 4.1 算法：在题目限制下选什么，而不是选最先进

候选包括：整段哈希派生向量、Unicode 字符 unigram/bigram/trigram + 带符号特征哈希、固定词表 BoW、冻结词表/IDF 的 TF-IDF、SimHash、MinHash、固定随机索引/投影。需要分别评判：

- 是否**自然符合** 256 维 `float[]`、相同输入严格一致、空文本全零、无需外部模型、异步与同步复用；
- 中文与英文、短文本、emoji、局部修改、词序颠倒、同义词、无关文档、零向量如何表现；
- 内存、CPU、实现与验证成本；固定 hash、规范化、排序、浮点操作、版本迁移和哈希碰撞的风险；
- 能否提供一个**可复现实验基准**，而不把主观评分、少量手工样本当成实际检索准确率。

已有调研倾向于“Unicode 字符 1+2 gram + 带符号特征哈希 + L2 归一化；余弦相似度 + Top-K 小顶堆”，但这只是候选方案，**希望 Pro 独立挑战并验证，而非照单全收**。

### 4.2 异步、并发与持久化

需回答：H2 持久任务与内存队列分别承担什么职责；提交事务与入队之间宕机怎么办；Worker 如何条件领取避免重复执行；哪些数据库字段需要原子更新；向量与成功状态如何原子提交；队列满时如何拒绝或背压；重启如何处理 `QUEUED/RUNNING`；线程池、CPU 模拟与同步查询竞争 CPU 时如何隔离；单实例方案的明确边界在哪里。

### 4.3 检索与统计

需回答：候选过滤、余弦相似度、稳定排序、K 大于候选数、分数为零或负值等边界；Top-K 小顶堆相对全量排序的实际价值；H2 查询与加载方式对内存的影响；并发检索命中计数如何避免丢失更新；失败请求与重复请求的计数语义如何定义。

### 4.4 开发和面试准备

需回答：开发前必须确认的规则、接口契约与数据模型；最小可运行代码结构与模块职责；单元测试、集成测试、并发测试、重启持久化测试及演示脚本；Git 提交节点和真实 AI 对话记录；面试官可能从代码、算法、线程和事务四个角度追问什么、如何回应设计取舍。

## 8. 推荐交付验收场景

1. 连续提交不同渠道文档：任务快速返回，有状态可查，未完成时无法进入检索。
2. 对完全相同、相似、无关、中文、英文、emoji 和空文本进行多次向量化：检查 256 维及严格确定性。
3. 不同 `topK`、渠道、失效状态与同分条件下，检索顺序和候选集合正确。
4. 任务计算中标记文档失效：完成任务不覆盖失效标志。
5. 多线程同时检索同一文档：命中计数不丢失。
6. 服务重启：已持久化文档与统计不消失；设计承诺恢复的未完成任务可继续处理。
7. 模拟容量边界和异常：队列饱和、非法参数、数据库故障、重复 ID；没有虚假成功及不可解释的永久挂起。
8. 在干净环境按 README 启动、执行测试和演示 API，检查真实 Git 历史和 AI 关键对话记录。
