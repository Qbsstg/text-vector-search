## 0. 总体判断与决策摘要

本项目首先是中高级 Java 工程实践题，其次才是 AI 应用题。交付的核心价值是：**可靠接收异步任务、确定性向量化、正确检索、并发安全、文件持久化与可解释的异常恢复**，而不是搭建完整 RAG。[P1，第1—3页]

| 决策 | 本次推荐 | 原因与边界 |
|---|---|---|
| 开发位置 | 本地开发与测试，CI 构建，服务器运行验收版 | 不让编译、Agent 和压测持续干扰演示；骨架完成就进行一次早期部署 |
| 服务器 | 推荐 2 vCPU / 4 GiB 内存 / 40 GiB SSD | 小规模、少量并发演示的资源起点，不是实测容量承诺 |

## 1. 业务分析与系统边界

### 1.1 功能的业务价值

真实知识库需要把“已经保存的文本”转成“可被查找到的知识”，并说明其来源、状态和是否仍有效。本服务可以作为智能客服、企业搜索或 RAG 的上游检索组件，但不生成答案。

| 使用者/调用方 | 诉求 | 本次提供 |
|---|---|---|
| 知识维护系统 | 提交文档后不等待计算完成 | 提交接口、任务 ID、状态查询 |
| 搜索/客服应用 | 根据描述获取候选知识 | 同步 Top-K、渠道过滤、原文与分数 |
| 运营或维护人员 | 撤回过时知识、解释为什么搜不到 | 文档列表、详情、失效及元信息 |
| 开发与评审人员 | 观察真实工程行为 | 简版演示页、API、测试、恢复和部署说明 |

业务价值不只有“搜到结果”，还有区分未完成、失败、失效、渠道不符和版本不兼容。渠道是来源标签，不是授权；命中次数是进入结果集合的统计，不是阅读量、点击量或答案正确率。[P4，第3—6节]

### 1.2 向量化与关键词/全文检索的差异

向量化把文本转成固定长度的可比较表示。关键词匹配适合精确编号、错误码等；全文检索可以使用 TF-IDF 等向量空间方法，并非都只是 SQL LIKE。这里的字符哈希向量保留局部字面重合，不代表理解同义词或语义。[A1、A2]

应特别说明：**“采用向量”与“采用真正语义模型”不是一回事。** 本题允许只模拟文本相似，不要求真实语义近似。[P1，第1页]

### 1.3 完整业务故事

以合成 FAQ“押金退款规则”为例，场景只是演示，不是招聘公司已确认业务。

1. 运营提交文档，服务在一个事务内保存文档与 QUEUED 任务，提交后返回 taskId。
2. 后台领取任务、生成向量；未完成时文档不能检索。
3. 成功事务同时保存向量、完成时间、任务终态。
4. 客服输入查询并选择渠道；服务计算同版本查询向量，对有效且就绪的候选评分，返回 Top-K。
5. 最终结果更新命中计数，展示来源和文档详情。
6. 规则过期后标记失效；历史详情保留，失效完成后发起的新检索必须排除该文档。
7. 重启后数据保留，遗留任务按单实例恢复规则处理。

首版不做原文覆盖更新。更新知识时使用新 ID；“新旧文档原子发布切换”不在范围内，不应宣称已经解决。

### 1.4 明确不做

不做真实 Embedding/LLM 调用、PDF/Word 解析、切片、聊天生成、RAG 编排、RBAC、多租户、外部 MQ、Redis、向量数据库、分布式调度、Kubernetes、数据大屏。公网演示的入口访问保护不等于实现了业务权限系统。

## 3. 算法选型：独立比较与推荐

### 3.1 先分清不同层次

n-gram 是特征提取；TF/TF-IDF 是加权；固定词表、哈希和随机投影是表示或降维；SimHash/MinHash 是签名；余弦/汉明/Jaccard 是比较方式。这些可以组合，不全是互斥算法。

令 L 为文本长度、F 为特征出现次数、D=256、V 为词表大小、R 为固定 CPU 计算轮数。所有交付结果都是 float[256]，原始载荷均为 1024 字节，不能直接借用 bit 签名的原生存储优势。

| 方案 | 确定性与固定维度 | 中文/相似性 | 典型 CPU 和额外状态 | 结论 |
|---|---|---|---|---|
| n-gram + 带符号哈希 | 规则固定后稳定，自然 256 维 | 中文不必分词，保留局部字符重合 | O(FR+D)，桶 O(D) | 首版默认，需承认碰撞与抵消 |
| 固定词表 TF/BoW | 256 槽位可固定 | 领域内易解释，词表外丢失信息 | 提取/查表通常 O(L)，词表 O(V) | 领域词表可靠时可考虑 |
| 冻结 TF-IDF | 冻结词表、IDF、映射后稳定 | 可用字符特征，不必依赖分词 | 加权 O(F)，另有模型及降维成本 | 合理但当前无训练资产，维护不划算 |
| SimHash→±1 float | 固定映射后可满足要求 | 角度/近重复签名，特征决定中文能力 | 常见 O(FD)，O(D) 累加器 | 可行，不应以“不是 float”否决 |
| MinHash | 固定签名后可稳定，float 编码需设计 | n-gram 集合 Jaccard，标准版本不保留频次 | 常见 O(FD)，O(D) | 本题编码与解释成本较高 |
| 整段哈希派生 | 固定、简单 | 小修改不保留局部结构 | 约 O(L+D) | 只作负对照，不作主方案 |
| 固定稠密随机投影 | 无需动态训练，可稳定 | 继承特征的字面关系 | O(FD)，按需生成方向可用 O(D) | 实质替代方案，值得实验 |
| 固定稀疏随机投影 | 可稳定，参数需固定 | 类似压缩词袋 | 每特征写少量坐标 | 可行，但首版不必增加参数面 |

上述是实现与数学分析，不是测评排名。参考算法背景见 [A1]—[A5]。

### 3.2 对既有结论的修正

**SimHash 可适配。** 256 维元素为 ±1 时，汉明距离为 h，则点积为 256−2h，两个范数均为16，因此 cosine=1−2h/256。其余弦排序与汉明距离排序精确对应。未优先采用的原因应是符号截断、常见实现运算成本和本题 float 存储下优势减少，而不是“接口不允许”。

**TF-IDF 并非天生不确定。** 不断重新拟合会变化；冻结模型就稳定。中文也可以用字符 n-gram 而非词级分词。当前缺少可靠语料和模型资产，才是首版不选的主要理由。[A2]

**固定随机投影不是只能作为理论备选。** 保留每维累计幅度、不进行 SimHash 符号截断，可以直接得到浮点向量。它可能在某些碰撞样例上优于单桶哈希，但必须实测，不能保证普遍更好。[A3]

**MinHash 不能把签名数字直接当连续向量求余弦。** 通常按签名位置相等率估计集合重合；32/64 位整数直接转 float 会丢精度，需要明示编码方案。[A4]

### 3.3 推荐算法的精确定义

保留原文；向量化使用固定规范化结果：NFKC、Locale.ROOT 小写、连续空白折叠、去首尾。按 code point 提取 1-gram 和 2-gram；空白作为边界，bigram 不跨空白，标点规则固定。给特征加入类型前缀，按固定 UTF-8 哈希分别决定桶与正负号，整数累计后按固定维度顺序归一化为 float[256]。

必须保证：每次调用独立累加数组；不共享可变 MessageDigest；范数为零返回零数组；检查 NaN/Infinity；向量字节序固定；零向量成功后仍是就绪。code point 不等于完整视觉字素簇，不夸大 emoji 处理能力。

把 JDK、规范化、特征、哈希、权重、轮数与归一化规则记录为算法版本。交付锁定同一运行时版本并保留黄金样例，不承诺任意 JDK 升级仍按位一致。

CPU 模拟采用有上限、固定轮数的真实确定性运算，不用 sleep 冒充。若重复哈希参与向量，必须逐特征稳定映射；不能把整篇文档摘要混进每个特征，否则共享片段不再映射到相同位置。查询与入库使用同一实现和配置。

### 3.4 可复现实验，而非编造准确率

必须测试工程性质：维度、空值、Unicode、按位重复、并发与跨进程一致、codec 往返、Top-K 对照全排序。

相关性实验另行准备固定文档集/查询集/人工标注，分离调参与保留查询。覆盖同文、局部修改、扩写、重排、同义改写、否定句、错误码、重复字符和字面相近但业务不同的干扰文档。

优先比较交付哈希、稠密固定投影、SimHash；整段哈希为负对照，未压缩 n-gram 余弦为压缩损失参考。固定规则后才记录 Recall@K、MRR 或 nDCG；没有标注不计算“准确率”。性能报告记录硬件、JDK、参数、预热、数据校验值和原始结果。

## 4. 技术架构与数据库

### 4.1 推荐架构

```text
浏览器 / API 调用方
        ↓ HTTPS + 入口访问保护
      Nginx
        ↓ 127.0.0.1:8080
单实例 Spring Boot（静态页面 + REST API）
  ├─ 提交：短事务保存文档和 QUEUED → 202
  ├─ 调度：扫描任务表 → 有界队列 → Worker → 条件领取
  │          → 事务外向量化 → 短事务保存向量和终态
  ├─ 检索：同步向量化 → 候选过滤 → 评分/Top-K → 原子计数
  └─ 管理：文档列表/详情/失效、任务查询
        ↓ MyBatis / JDBC（进程内，无数据库网络端口）
      H2 文件库（独立持久目录）
```

### 4.2 为什么不需要 MySQL

原题明确要求 H2 嵌入式数据库与文件持久化，所以 H2 在这里是正式运行数据源，不只是测试替身。[P1，第2页]

H2 通过 Java 依赖在应用进程内运行，数据写入文件。只需 Java 应用依赖与可写目录，不需安装独立 H2 服务，也不需要启动 MySQL、Redis 或云数据库。[S1]

禁止采用“本地 H2，服务器 MySQL”的双数据库模式交付本题。它改变要求并增加 SQL、事务与初始化差异。未来生产化是否更换数据库，是独立议题。

### 4.3 数据模型

| 表 | 字段组 | 约束/责任 |
|---|---|---|
| documents | document_id、raw_text、channel、submitted_at | ID 主键，原文不可覆盖，渠道非空 |
| documents | invalidated、invalidated_at | 仅失效逻辑更新 |
| documents | vector_bytes、embedding_version、vector_completed_at | 仅成功任务事务更新 |
| documents | hit_count BIGINT | 初始0，检索原子自增 |
| embedding_tasks | task_id、document_id、status | task主键，document外键且首版唯一 |
| embedding_tasks | embedding_version、run_token、attempt_count | 版本与执行尝试标识 |
| embedding_tasks | submitted_at、started_at、finished_at、error_code/error_message | 跟踪与有界、脱敏错误 |

向量二进制固定 1024 字节，固定字节序；不使用 Java 原生序列化。vectorReady 从成功状态和向量存在推导，不增加可独立修改的冗余标记。任务状态与文档失效状态正交。[P2，第6节]

索引首先考虑任务状态/提交时间/ID、任务关联文档唯一键、文档渠道和失效过滤；实际效果看 EXPLAIN 和测试，不提前承诺优化收益。

### 4.4 技术版本

使用 Java17、Spring MVC、MyBatis、Bean Validation；测试依赖按所选 Boot BOM 管理，不将不同代际测试栈随意拼接。

本次官方资料显示 Boot 4.1.1 仍以 Java17 为最低要求；MyBatis 官方仓库分别列出4.1与4.0分支对应的 Boot 代际。建议新建时锁定经过最小启动验证的配套稳定版本；已验证4.0组合则无须临近交付强行升级。[S3、S4]

精确补丁版本以实际解析、启动和测试为准，不能把“4.x 都兼容”当作已运行证据。

建表使用随项目交付的schema.sql和幂等CREATE TABLE/INDEX IF NOT EXISTS，显式配置spring.sql.init.mode=always；DDL失败应阻止启动。自动建表不等于完整历史schema迁移，不混用Hibernate的create/create-drop。[S20]

| GET /api/documents | 分页列表 | 元信息、taskId/taskStatus、vectorReady/invalidated |
| GET /api/documents/{documentId} | 文档详情 | 原文、状态、来源、时间、命中数 |
| PUT /api/documents/{documentId}/invalidation | 幂等失效 | 首次失效时间与当前状态 |
| POST /api/search | text、topK、可选channel | hits 数组，score按降序、同分按ID升序 |

以下规则属于本版建议：

- 文档ID重复409；null文本400；空字符串合法；纯空白按规范化规则处理。不要给text使用@NotBlank。
- 提交省略channel时为default；检索省略channel时是全渠道。显式空白channel为400。此前材料存在不同空白默认建议，本版作了明确取舍。
- topK范围1—100；K大于候选数返回全部；不额外设置相似度阈值；零分负分允许进入结果。
- 空查询按照零向量、无阈值Top-K规则返回稳定零分结果，并正常统计；页面明确提示无相关性区分。这不是原题强制规定，而是保持与上一轮契约一致。
- 失效幂等且保留首次时间；不做恢复有效、原文覆盖、手动重试接口。
- 时间以UTC ISO-8601传输，页面显式显示北京时间。
- 接口只返回必要文本，列表不下发向量；最终分数不是概率或置信度。

## 6. 并发、事务与任务恢复

### 6.1 核心不变量

1. 可检索 = 任务成功 + 向量存在 + 文档有效 + 算法版本一致。
2. 向量、完成时间和任务成功必须原子提交。
3. Worker 不修改失效和命中字段。
4. 内存队列丢失不能导致已持久接收的任务消失。
5. 只给最终Top-K计数，不给扫描候选计数。

### 6.2 队列设计

采用固定大小ThreadPoolExecutor + ArrayBlockingQueue，Runnable只携带taskId，拒绝策略AbortPolicy。不要使用第二层无界执行队列。内存满则调度器暂停派发，H2的QUEUED保留等待；CallerRunsPolicy可能使提交线程承担计算，丢弃策略会隐藏丢任务风险。[S5]

原题没有要求重写阻塞队列，使用JDK队列并自行实现调度逻辑即可。newFixedThreadPool的默认无界队列不适合用来表达整体容量控制。[S6]

### 6.3 接收容量与实际提交边界

内存队列容量与持久未完成任务上限分开控制。单实例接收锁应覆盖“检查容量—插入两表—真实提交”。可用TransactionTemplate在锁内提交，不能方法返回后由代理才提交，也不能在外层事务存在时误认为内层回调返回就已经物理提交。[S7]

所有新增未完成任务的路径共享控制。首版没有手动重试，避免引入旁路。

### 6.4 持久化成功但入队失败

| 故障点 | 数据库状态 | 恢复 |
|---|---|---|
| 提交前失败 | 文档与任务都回滚 | 用户重新提交 |
| 提交后、入队前崩溃 | QUEUED | 扫描补派 |
| 入队后、领取前崩溃 | QUEUED | 重启补派 |
| 领取后、计算中崩溃 | RUNNING | 启动恢复为QUEUED重算 |
| 完成事务未提交 | 不应存在半成功 | 重启后按持久状态恢复 |
| 完成提交后崩溃 | SUCCEEDED | 不重复完成 |

提交后的主动唤醒只是降低延迟的优化，不代替周期扫描。

### 6.5 条件领取、幂等与令牌

在途ID集合仅减少重复派发；数据库`WHERE status='QUEUED'`的条件更新且受影响行数为1，才是领取成功证据。领取产生run_token。结束时必须匹配RUNNING与该令牌；失败的条件更新不允许继续写文档向量。

计算放在事务外；成功回写两表放在同一个短事务，任何条件失败都回滚。run_token不是完整分布式租约；首版不声称支持跨实例抢占。

Spring代理模式下，同类自调用的@Transactional并不会按期待触发事务，应通过结构和回滚测试证明边界。[S8]

### 6.6 向量完成与失效竞态

错误：Worker读到invalidated=false旧实体，管理员失效，Worker整体保存旧实体把失效覆盖。

正确：失效仅更新失效字段；Worker只更新向量和完成字段。允许“任务成功且文档失效”。测试用latch控制先计算、后失效、再完成，验证不会复活。

### 6.7 检索与失效语义

以一次候选读取所得结果集为本次计算基础：失效完成后新开始的检索必须排除；重叠的在途检索允许返回之前读到的候选。

不要把这叫作全系统SERIALIZABLE隔离，也不要声称最后再查一遍就能保证响应送达时绝无失效结果。二次检查后仍可能有竞态；网络送达时间更无法以一次SQL保证。

### 6.8 命中计数

采用SQL `hit_count=hit_count+1`，禁止Java读改写。最终K条在一个短事务内按固定ID顺序更新，以降低交叉锁顺序风险。

命中定义为结果选择与计数事务成功提交：提交后客户端断开仍已计数，客户端重试会再次计数。已确认回滚可有限重试；提交结果未知时不能盲目重试自增，否则可能重复计数。检索因此不是只读请求。

### 6.9 回写失败与恢复边界

计算成功、终态写入失败不能只打日志留下永久RUNNING。对明确可重试错误有限重试；提交结果未知先查询确认状态。无法确认时显式降级、停止新接收、保留诊断，修复数据库后按恢复说明重启。

首版不做在线超时抢占：运行久不代表Worker已经死亡。启动恢复仅在单实例、旧进程已退出的前提下进行。恢复完成前实际业务入口关闭，不只是健康页显示未就绪。

正常停止先停接收和派发，等待在途任务有界结束，最后关数据源。不要无差别中断正在操作嵌入式H2的线程；进程崩溃测试应使用独立测试进程与文件。[S1]

## 7. 并行处理的真正压力在哪里

### 7.1 开发Agent并行与业务线程并行是两个问题

Agent并行是多个开发会话生成/审查代码；业务并行是服务器处理文档任务与HTTP请求。增加Agent不会增加部署服务器性能，增加Worker也不能缩短人工审查时间。

### 7.2 两条链路的压力

```text
入库：短事务保存原文/任务 → 后台CPU向量化 → 短事务保存1KiB向量与终态
检索：同步CPU向量化 → 读取N条候选 → N×256维评分 → Top-K → K条命中写入
```

**不能笼统判断“压力都在向量存库”。** 每条向量原始数据只有1KiB，但入库CPU轮数、文本长度、数据库刷盘、搜索全扫描、并发复制和热点统计都可能成为瓶颈。

| 负载 | 更可能的压力 | 应测什么 |
|---|---|---|
| 批量长文入库 | 向量化CPU、排队、接收事务 | 每任务CPU时间、队列等待、积压 |
| 文档数量增加且频繁搜索 | 候选读取、N×D计算、请求内存 | N变化时阶段耗时、GC、RSS |
| 查询CPU模拟轮数很高 | 查询向量化本身 | 查询长度/轮数与CPU关系 |
| 大量搜索反复命中少数文档 | hit_count行锁与事务提交 | 锁等待、统计事务耗时 |
| 很慢磁盘或严格刷盘 | H2提交I/O | 提交延迟、iowait、磁盘空间 |
| 多人同时开任务页面 | 轮询放大 | GET QPS、轮询并发与停止条件 |

理论关系（不是实测）：后台到达率λ_doc超过实际完成率μ_doc时，积压会增长；异步只把等待移到队列，不会创造CPU。单查询耗时包括queryEmbedding + candidateRead + score + topK + hitCommit。CPU需求可按各类请求率乘以实测CPU秒估算，不能拿HTTP墙钟时间代替CPU时间。

### 7.3 Top-K与内存

时间：O(ND + N log K + K log K)。堆O(K)，但一次加载全部候选仍需O(ND)。N=10000时原始向量约9.77MiB，C个请求私有复制约C倍，未计对象、字节数组、H2缓存与原文。

不在候选阶段读原文大字段，最终K条再取必要原文；不建立共享可变向量缓存。也不能为节省内存悄悄只扫描最新1000条，那会改变全库Top-K语义。

### 7.4 初始参数与观察

2核4GiB建议先用后台Worker=1、同时搜索许可=1、内存队列=64、待处理任务上限=1000、文档上限=5000、topK/pageSize≤100、原始及规范化文本≤20000 code points、请求体≤256KiB。均为待测起点。

先测纯入库、纯检索、混合负载和热点计数四组；压测客户端在另一台机器，控制数据、并发、轮数和持续时间。记录p50/p95、CPU、RSS、GC、队列等待、数据库阶段耗时、错误/拒绝数。结果决定加核、限流、降轮数或改读取方式，不能未经测量就换数据库。

## 8. 开发与部署策略

### 8.1 推荐本地开发，但提前验证部署

推荐流程：本地代码/测试 → GitHub/CI → 固定提交SHA的JAR → 上传服务器 → 重启单实例 → 冒烟验证。

骨架完成当天就部署一次健康检查与静态页面，提前暴露JDK、目录权限、反向代理、防火墙和证书问题。不要等所有功能写完才第一次登录服务器。

不建议在唯一演示服务器上直接开发：测试污染H2、多个进程争文件锁、编译争CPU、SSH中断和凭据暴露都会增加风险。

本地环境确有障碍时可用独立远程开发环境；必须不同端口、数据目录和系统用户，不共享演示H2，不以root运行Agent。远程开发与生产演示最好分机；不能分机则串行安排构建和展示。

### 8.2 服务器配置

以下是资源预算建议，假设少量评审者、合成文本、千级文档，无本地模型、无GPU。

| 档位 | 资源 | 适用范围与限制 |
|---|---|---|
| 节省预算 | 2 vCPU / 2 GiB / 20—40 GiB SSD | 单人低负载演示，需要更紧的JVM和并发限制；不在机上构建 |
| **推荐** | **2 vCPU / 4 GiB / 40 GiB SSD** | 后端+静态页面+H2+Nginx，留运行与诊断余量 |
| 开发测试合用或较多并行 | 4 vCPU / 8 GiB / 40—60 GiB SSD | 多构建/测试进程或并行演示；仍优先避免共机干扰 |

可从3—5Mbps公网带宽起步，仅是少量文本演示的规划值；长原文、大topK和多人访问会改变需求。云主机共享核、突发积分及磁盘性能会影响测试，不能只看“2核”标签。无需GPU或付费数据库实例。

建议采用熟悉且仍受支持的Linux LTS，例如Ubuntu24.04 LTS，并核对镜像和补丁状态。[S9]

4GiB机器可从-Xms256m -Xmx1024m起测，JVM堆包括H2和请求向量，不能再重复计算一份独立“H2进程内存”；非堆、线程栈、OS、代理和页缓存另占资源。堆上限不等于进程RSS上限。

### 8.3 部署、安全与持久数据

推荐JAR+systemd+Nginx，前端放入Spring Boot静态资源目录，服务绑定127.0.0.1:8080。systemd可负责开机启动与失败重启，但进程存活不等于任务功能健康。[S10、S11、S12]

目录建议：

```text
/opt/vector-search/releases/<git-sha>/app.jar
/opt/vector-search/current -> releases/<git-sha>
/var/lib/vector-search/db/knowledge.mv.db
/etc/vector-search/app.env
/var/backups/vector-search/
```

数据库URL使用固定绝对路径，例如`jdbc:h2:file:/var/lib/vector-search/db/knowledge;WRITE_DELAY=0`。WRITE_DELAY=0是减少异步刷写窗口的取舍，不是断电零丢失保证，须测提交成本。[S1、S2]

Nginx负责HTTPS和入口认证；认证覆盖页面和API，不能只保护首页。8080不对公网开放；不开放H2 TCP/Console，不暴露env、heapdump等管理端点。敏感操作不能用GET，JSON接口拒绝不符合契约的Content-Type，不配置任意来源CORS；Basic Auth不是完整CSRF防护，浏览器写操作还应校验同源Origin或使用CSRF机制。

只用合成数据，认证凭据单独交付评审，不写前端和Git。没有HTTPS时先用SSH隧道/VPN等受控访问完成验收，不在明文公网传账号密码。

H2文件不能放release、target、Git仓库或未挂载持久卷的容器可写层。不能两个应用实例同时打开这套嵌入式库；不做蓝绿同时挂同库。备份优先正常停止后复制，或采用H2支持的在线备份；不要运行中直接cp活动数据库文件。回滚先检查表结构兼容，程序回滚不等于数据回滚。[S1、S13]

## 9. GitHub组织与交付建议

采用一个仓库承载后端、静态前端、部署样例、测试、设计与AI记录。保留原始真实提交，不最后伪造大量提交。[P1，第2—3页]

```text

src/main/java/.../{api,document,task,embedding,search,persistence,config}
src/main/resources/{application.yml,schema.sql,static/}
src/test/java/...

scripts/            # 演示、部署、验收；不得硬编码密钥
.github/workflows/ci.yml
AGENTS.md / README.md / .gitignore
```

建议先私有，确认招聘方允许公开后再调整。原题PDF、公司名、实际客诉和原始AI对话不应未经检查直接公开；AI关键对话保留决策过程并脱敏。公开源码不意味着允许公开招聘资料。

CI先做到JDK17 + Maven Wrapper + clean verify，确保集成测试实际被执行。*IT测试若未配置Failsafe，不会因运行verify就自动得到覆盖。测试报告与JAR产物关联SHA；建议手动审批部署，首版不建立生产自托管Runner。[S14、S21]

权限遵循最小化，Actions引用固定可信完整SHA；密钥使用受保护的凭据存储。若密钥已进入历史，应先撤销/轮换，删除当前文件不能消除泄漏。[S15、S16]

.gitignore排除target、运行数据、日志、.env、私钥和本地IDE文件。初期不需要复杂GitFlow；短分支+人工审查足够。发布v0.1.0-demo时记录源码SHA、构建环境、JAR校验和、演示地址与真实已通过/未执行项目。GitHub是源码和CI平台，不是本项目Java/H2运行服务器。

## 10. 多Agent协作

### 10.1 采用轻量并行，而非角色扮演式过度拆分

建议一个主控负责契约、集成和审查，后端一名保持事务与状态机整体所有权，前端和部署可以并行，测试角色提早写验收用例、后期验证。

| 角色 | 负责 | 不可自行修改 |
|---|---|---|
| 主控（你+主Agent） | 需求、API、DDL、版本、合并、验收 | 不把关键正确性审查完全外包 |
| 后端 | 核心Java/Mapper、向量器、任务、检索 | 不无通知改JSON契约或生产配置 |
| 前端 | static下页面/CSS/JS、前端测试 | 不修改数据库/Java/接口字段 |
| 部署 | deploy脚本、systemd、代理、CI建议 | 不拿到长期云主密钥，不私自发布 |
| 测试 | 独立验收、竞态/恢复用例、问题报告 | 不为了通过而降低断言或改业务语义 |

官方Codex资料支持子Agent协作与worktree隔离；具体界面入口以安装版本和账户实际功能为准。本方案不依赖某个按钮存在，可用多个会话+Git worktree执行。[S17、S18]

最多2—3个写入任务同时进行。4个角色不等于4个角色必须常驻并行。小项目的串行链仍是：契约 → 核心后端 → 真接口联调 → 故障验证 → 发布。合并与审查时间不能被省略。

### 10.2 隔离条件

每个写入Agent使用独立分支/worktree，不共享工作目录；测试服务有独立端口和临时H2路径。Git工作树隔离文件，不隔离CPU、端口、环境变量和数据库，仍需显式分配。[S19]

pom.xml、schema.sql、基础application配置和api-contract由主控掌握；变更先提议再执行。每次交付提供commit、修改文件、命令与真实结果、未验证点。禁止不同Agent同时进行生产部署和全仓格式化。

详细可复制任务说明见`04_多Agent任务拆分与Codex指令.md`。

## 11. 简版前端定位

一个“文本检索演示台”，不是聊天机器人，不需要前端服务器或复杂Vue/React工程。

三个功能区：**检索体验、文档管理、任务追踪**。详情用抽屉；文档提交后显示真实taskId和后端状态；轮询终态停止；统计和分数从API读取，不生成模拟进度。页面以检索默认tab打开，桌面优先、小屏可用。

原生HTML/CSS/JS由Spring Boot同源提供，减少构建依赖、跨域和部署节点。[S12] 熟悉Vue的开发者也可采用打包静态资源，但不为本题临时搭建复杂前端栈。

完整页面字段、错误状态、轮询与验收见`03_简版前端产品设计文档_PRD.md`。

| T13 | 数据库回滚与提交结果未知 | 不假成功、不盲目重复计数 |
| T14 | 资源超限、非法参数、饱和 | 明确400/413/409/429/503等 |
| T15 | 真实UI与API联调 | 空/错/成功/失效状态一致，无XSS |
| T16 | 服务器停止、启动、更新与备份恢复 | 同库持久、版本可追踪、授权访问 |
| T17 | 混合负载与热点测试 | 记录真实瓶颈，不伪造性能 |
| T18 | 新目录/新机器复演 | README足以独立启动与演示 |

异步竞态用latch/barrier控制，避免靠sleep猜时序。正常关闭重启不是崩溃恢复；注入SQLException也不是实际断电测试。页面显示在线不等于所有后台任务健康。
